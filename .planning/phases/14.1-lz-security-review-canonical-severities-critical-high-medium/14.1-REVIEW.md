# Phase 14.1: Code Review Report

**Reviewed:** 2026-06-14
**Depth:** standard
**Files Reviewed:** 4
**Status:** issues_found

## Summary

Phase 14.1 migrates the security-review output taxonomy from `Critical/Important/Suggestions/Questions` to canonical `Critical/High/Medium/Low/Informational` + a non-severity `Open Questions` section, in a single atomic commit (36960ae). The change touches three Markdown prompt-contract files and one executable bash regression fixture.

The core executable code -- `tests/D-security-reviewer-budget.sh` -- is sound. I ran it in all three modes: default `self-extract` (12/12 PASS, exit 0), `--self-test` (correctly trips the anti-vacuous guard, exit 1), and a synthetic `--from-trace` (correctly FAILS an over-cap Informational-with-CVE finding). The new `FINDING_SEVS` parallel-array tracking and the D-14 section-aware 28w cap on `### Informational` are correct: indices stay in lockstep with `FINDING_BODIES`, quoting is safe under `set -euo pipefail`, and the `--self-test` non-zero exit contract holds. No budget constant was loosened (22/28/75/60/160/30/15 all preserved).

The migration is, however, NOT complete. Two genuine defects survive the commit:

1. The Verification Consultation Template in `context-packaging.md` -- which the lz-security-review skill explicitly uses for its Phase 2 consultation -- still instructs the executor to assign initial security severity as `Critical/Important/Suggestion`. This is the residual old-taxonomy / mixed-vocabulary bug the phase set out to eliminate.
2. The `<auto_clarity_carve_out>` XML element in the agent's `<output_constraints>` block lost its closing tag during this commit, leaving three sibling `<section>` elements improperly nested inside it.

A third quality concern: the regression fixture's own default mode does not actually exercise the new D-14 override (the holistic example's Informational finding carries no CVE bracket), so the green gate does not regression-protect the new logic.

## Warnings

### WR-01: Residual old taxonomy in the security-review consultation template (mixed-vocabulary drift)

**File:** `plugins/lz-advisor/references/context-packaging.md:290-291`
**Issue:** The Verification Consultation Template's `## Findings` structure still reads:

```
  - Severity (initial): [Critical/Important/Suggestion for review;
    Critical/Important/Suggestion for security-review]
```

The lz-security-review skill explicitly packages its Phase 2 consultation per this template (SKILL.md:137-138: "Package the consultation prompt per the Verification template in ... context-packaging.md"). So the executor is told to assign initial **security** severities from the OLD vocabulary, directly contradicting:
- the same skill's scan phase (SKILL.md:127): "Critical / High / Medium / Low for vulnerabilities; Informational ...";
- the security-reviewer agent's canonical 5-tier headers;
- the enum-fork annotation this very commit added at context-packaging.md:390 ("the security-reviewer uses the canonical security scale `critical|high|medium|low|informational`").

This is the WR-05 few-shot-drift / mixed-vocabulary failure mode the phase set out to remove. The single-line diff at line 390 updated the `<verify_request>` `severity=` enum description but missed the template body that the skill actually drives the executor with. The `for review` half of the same line is correctly OLD (the reviewer fork keeps `Important/Suggestion`); only the `for security-review` half is wrong.

**Fix:** Update line 290-291 to fork the security-review severities to the canonical scale:
```
  - Severity (initial): [Critical/Important/Suggestion for review;
    Critical/High/Medium/Low/Informational for security-review]
```

### WR-02: Unclosed `<auto_clarity_carve_out>` element nests three sibling sections (XML malformation introduced by this commit)

**File:** `plugins/lz-advisor/agents/security-reviewer.md:303`
**Issue:** Before this commit the element was self-contained on one line, properly closed (diff line 226):

```
<auto_clarity_carve_out cap="75">A finding whose body carries ... full prose.</auto_clarity_carve_out>
```

This commit expanded the element body to add the D-14 Informational-denied clause but **dropped the closing `</auto_clarity_carve_out>` tag** (diff line 227 / file line 303). As a result the `<section name="per_finding_validation">` (304-311), `<section name="threat_patterns">` (312-314), and `<section name="missed_surfaces">` (315-317) elements are now syntactically nested INSIDE the unclosed carve-out element rather than being its siblings under `<output_constraints>`. This is a regression: a previously well-formed prompt-contract block is now malformed. Opus parses XML-tagged prompt structure (the whole point of the `<output_constraints>` block per context-packaging.md Rule 5b), so a mis-nested element can degrade the structural binding the block exists to provide.

**Fix:** Close the element immediately after its prose, before the `<section name="per_finding_validation">` line:
```
  <auto_clarity_carve_out cap="75">A finding under ... without the long form.</auto_clarity_carve_out>
  <section name="per_finding_validation" type="repeating" optional="true">
```

### WR-03: Regression fixture default mode does not exercise the new D-14 override

**File:** `tests/D-security-reviewer-budget.sh:262-266` (logic), `plugins/lz-advisor/agents/security-reviewer.md:244` (the example that should exercise it)
**Issue:** The commit adds the D-14 section-aware override (force hard 28w cap, deny the 75w auto-clarity escape under `### Informational`). The override is correct -- I proved it with a synthetic `--from-trace` input (a 44-word Informational finding carrying `[CVE-2025-9999]` correctly FAILED). But the committed default `self-extract` run never reaches the override's effect: the holistic example's only Informational finding (finding 7, "response omits a security header on this JSON-only API ...") carries NO `[CVE]`/`[GHSA]`/`[CWE]` bracket, so `is_auto_clarity` is already 0 and the D-14 branch changes nothing observable. The default green gate therefore passes identically whether or not the D-14 override exists -- the new logic ships without self-regression-protection in the fixture's primary mode.

**Fix:** Add a `[CVE]`/`[GHSA]`/`[CWE]`-bracketed Informational finding (within 28w) to the holistic worked example in `security-reviewer.md`, OR add a dedicated `--self-test`-style negative case (an over-28w Informational-with-CVE finding that must FAIL) so the default `bash tests/D-security-reviewer-budget.sh` run distinguishes "D-14 present" from "D-14 absent". Note the agent prose at line 303 explicitly sanctions "A bare [CWE-xxx] class reference may still appear in an Informational entry without the long form", so a short `[CWE-xxx]` Informational finding is a contract-legal way to cover this.
