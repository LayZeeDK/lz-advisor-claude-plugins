<decisions>
## Implementation Decisions

### Severity Model

- **D-01:** Adopt the canonical 5-tier scale -- `### Critical` / `### High` / `### Medium` / `### Low` / `### Informational`. This SUPERSEDES the SEED + ROADMAP "Critical/High/Medium" 3-rung framing; it is the user's informed override after canonical web research showed every major security ladder (CVSS/GHSA/OWASP/Dependabot/pentest) carries Low + an Informational/observation tier. ROADMAP goal text + the Phase 15 CHANGELOG must read `C/H/M/L/Informational`.
- **D-02:** `Critical/High/Medium/Low` are exploitable-*vulnerability* rungs ordered by impact x exploitability. `### Informational` is best-practice hardening / defense-in-depth / *observations* with NO direct exploitable risk -- it is NOT a vulnerability rung.
- **D-03:** Old -> new mapping: `Critical -> Critical`; `Important -> High`; `Suggestions` DISSOLVES (re-triage each finding: minor-exploitable -> `Low`, hardening/no-exploit -> `Informational`); `Questions -> Open Questions` (see D-08).

### Empty-Section & Curation Semantics

- **D-04:** Omit-when-empty for the security report -- a severity tier section is emitted ONLY when it has >=1 finding; NO `(none)` markers. This reverses the v1.0.1 always-emit-with-`(none)` rule FOR security-review only. Rationale: `(none)` under a severity is a false-assurance because the agent curates only the top 3-5 findings (not an exhaustive census), so an empty section asserts an absence the review cannot actually certify.
- **D-05:** Fixed RELATIVE order among populated sections: `### Critical` -> `### High` -> `### Medium` -> `### Low` -> `### Informational` -> `### Open Questions` -> `### Per-finding validation` (optional) -> `### Threat Patterns` (required, always) -> `### Missed surfaces` (optional).
- **D-06:** Priority curation -- the top-3-5 finding cap governs VULNERABILITIES (`C/H/M/L`); higher severities fill the curation slots first. `Informational` is appended BEYOND the vulnerability cap (canonical practice lists Informational separately from key findings), capped at **<=5 Informational entries**, all within the existing `max_count=15` ceiling. This delivers the "useful on clean code" value without Informational competing for the vulnerability slots.

### Completeness Caveat

- **D-07:** Add a one-line completeness caveat SKILL-SIDE, in the `## Security Review Summary` header (next to `Reviewed: [scope]`). Exact locked wording: `Scope note: a curated set of the highest-priority findings in the reviewed code at this point in time -- not an exhaustive audit. An absent severity is not a guarantee that none exist.` Skill-side placement = ZERO added migration surface on the agent grammar or budget fixture. It positively defuses the misleading-absence problem that omit-when-empty alone leaves open; canonical practice (NIST SP 800-115, PTES).

### Open Questions & Pending/Hedge Content

- **D-08:** Rename `### Questions` -> `### Open Questions` (non-severity, omit-when-empty) -- the home for genuinely un-ratable author-clarification questions (severity conditional on author intent, e.g. "Is this endpoint authenticated?").
- **D-09:** Retarget the Hedge Marker Discipline's now-dead "unconfirmed security-clearance hedge -> `### Suggestions`" rule to "-> `### Open Questions`". Preserve the literal `Unresolved hedge:` token verbatim (the executor greps for it); promote the finding to a real severity rung once verification confirms the threat.
- **D-10:** Reviewer-introduced provisional premises stay INLINE at their severity rung via the existing `Assuming X (unverified), do Y. Verify X before acting.` frame (UNCHANGED). `<verify_request>` escalation hooks continue trailing their affected finding inside that finding's section (UNCHANGED).

### Machine Vocabulary

- **D-11:** The `<verify_request severity="...">` enum realigns from `critical|important|suggestion` to `critical|high|medium|low|informational` (lowercase machine attrs mirror the display tiers, per the Phase 12 precedent of keeping machine attrs lowercase-but-aligned). Un-ratable Open Questions items carry their suspected/provisional tier or omit the attribute.

### Low vs Informational Adjudication

- **D-12:** Binary triage test the agent applies per finding: **"Is there a concrete exploitation path, however minor or conditional?"** -- Yes -> a vulnerability rung (minor path -> `Low`); No -> `Informational` (hardening/observation). Ties to the agent's existing `## Boundaries` ("check the data flow before raising the finding"). Locked worked anchors: missing security header on a JSON-only API (Informational) vs on sniffable user-content (Low); deprecated dependency with no CVE (Informational) vs with a CVE (Low+); verbose error leaking framework version (Informational) vs a DB connection string (High/Critical).

### Word Budgets & Cost Control

- **D-13:** Per-entry caps replicate UNIFORMLY across all 5 severity tiers + `### Open Questions`: `22w` target / `28w` outlier soft cap / `75w` CVE-GHSA-CWE auto-clarity. `Threat Patterns` 160w, `Per-finding validation` 60w, `Missed surfaces` 30w, `max_count` 15 -- all unchanged.
- **D-14:** `Informational` is DENIED the 75w auto-clarity escape (hard `<=28w`). The 75w carve-out stays `C/H/M/L`-only (CVE/GHSA/CWE advisories). Forcing function: a "hardening" note that genuinely needs 75w has an exploitation path and therefore belongs on the vulnerability ladder, not Informational. A CWE class reference may still appear as a bare `[CWE-xxx]` bracket without the long form.
- **D-15:** `### Threat Patterns` stays REQUIRED-always (not omit-when-empty) -- it is analytical value-add, "No chaining -- findings independent" is meaningful (not an absence-claim), and the fixture already asserts the header present and fails loudly if missing.

### Informational Cost-Control Guardrails

- **D-16:** The executor never HUNTS for hardening -- `Informational` items are noted only opportunistically while triaging the real attack surface; "find hardening opportunities" is NEVER a Phase 1 scan goal (guards the documented executor over-investigation failure mode).
- **D-17:** The advisor never spends tool-use turns (Read/Glob) VERIFYING Informational -- hardening notes are emitted from in-context material only, protecting the `maxTurns: 3` / `effort: medium` verification budget for real threats.
- **D-18:** `Informational` is explicitly OPTIONAL, and a `<do_not_include>` item forbids manufacturing or padding hardening notes to fill the section.

### Claude's Discretion

- The two knobs the user delegated ("you decide or consult an agent") were decided directly (not via an advisor consult -- the plugin's own discipline reserves consults for high-leverage architectural moments, not calibration): the `Informational` count cap = `<=5` (D-06) and denial of the 75w escape for Informational (D-14). Guardrails D-16/D-17/D-18 were also locked at Claude's discretion within the user's cost-control directive.

</decisions>
