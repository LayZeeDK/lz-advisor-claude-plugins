### Locked Decisions

**Severity Model**
- **D-01:** Adopt the canonical 5-tier scale -- `### Critical` / `### High` / `### Medium` / `### Low` / `### Informational`. This SUPERSEDES the SEED + ROADMAP "Critical/High/Medium" 3-rung framing. ROADMAP goal text + the Phase 15 CHANGELOG must read `C/H/M/L/Informational`.
- **D-02:** `Critical/High/Medium/Low` are exploitable-*vulnerability* rungs ordered by impact x exploitability. `### Informational` is best-practice hardening / defense-in-depth / *observations* with NO direct exploitable risk -- it is NOT a vulnerability rung.
- **D-03:** Old -> new mapping: `Critical -> Critical`; `Important -> High`; `Suggestions` DISSOLVES (re-triage: minor-exploitable -> `Low`, hardening/no-exploit -> `Informational`); `Questions -> Open Questions` (see D-08).

**Empty-Section & Curation Semantics**
- **D-04:** Omit-when-empty for the security report -- a severity tier section is emitted ONLY when it has >=1 finding; NO `(none)` markers. Reverses the v1.0.1 always-emit-with-`(none)` rule FOR security-review only. Rationale: `(none)` under a severity is false-assurance because the agent curates only the top 3-5 findings.
- **D-05:** Fixed RELATIVE order among populated sections: `### Critical` -> `### High` -> `### Medium` -> `### Low` -> `### Informational` -> `### Open Questions` -> `### Per-finding validation` (optional) -> `### Threat Patterns` (required, always) -> `### Missed surfaces` (optional).
- **D-06:** Priority curation -- the top-3-5 finding cap governs VULNERABILITIES (`C/H/M/L`); higher severities fill curation slots first. `Informational` is appended BEYOND the vulnerability cap, capped at **<=5 Informational entries**, all within the existing `max_count=15` ceiling.

**Completeness Caveat**
- **D-07:** Add a one-line completeness caveat SKILL-SIDE, in the `## Security Review Summary` header (next to `Reviewed: [scope]`). Exact locked wording: `Scope note: a curated set of the highest-priority findings in the reviewed code at this point in time -- not an exhaustive audit. An absent severity is not a guarantee that none exist.` Skill-side placement = ZERO added migration surface on the agent grammar or budget fixture.

**Open Questions & Pending/Hedge Content**
- **D-08:** Rename `### Questions` -> `### Open Questions` (non-severity, omit-when-empty) -- home for genuinely un-ratable author-clarification questions.
- **D-09:** Retarget the Hedge Marker Discipline's now-dead "unconfirmed security-clearance hedge -> `### Suggestions`" rule to "-> `### Open Questions`". Preserve the literal `Unresolved hedge:` token verbatim (the executor greps for it); promote the finding to a real severity rung once verification confirms the threat.
- **D-10:** Reviewer-introduced provisional premises stay INLINE at their severity rung via the existing `Assuming X (unverified), do Y. Verify X before acting.` frame (UNCHANGED). `<verify_request>` escalation hooks continue trailing their affected finding inside that finding's section (UNCHANGED).

**Machine Vocabulary**
- **D-11:** The `<verify_request severity="...">` enum realigns from `critical|important|suggestion` to `critical|high|medium|low|informational` (lowercase machine attrs mirror the display tiers). Un-ratable Open Questions items carry their suspected/provisional tier or omit the attribute.

**Low vs Informational Adjudication**
- **D-12:** Binary triage test the agent applies per finding: **"Is there a concrete exploitation path, however minor or conditional?"** -- Yes -> a vulnerability rung (minor path -> `Low`); No -> `Informational`. Locked worked anchors: missing security header on a JSON-only API (Informational) vs on sniffable user-content (Low); deprecated dependency with no CVE (Informational) vs with a CVE (Low+); verbose error leaking framework version (Informational) vs a DB connection string (High/Critical).

**Word Budgets & Cost Control**
- **D-13:** Per-entry caps replicate UNIFORMLY across all 5 severity tiers + `### Open Questions`: `22w` target / `28w` outlier soft cap / `75w` CVE-GHSA-CWE auto-clarity. `Threat Patterns` 160w, `Per-finding validation` 60w, `Missed surfaces` 30w, `max_count` 15 -- all unchanged.
- **D-14:** `Informational` is DENIED the 75w auto-clarity escape (hard `<=28w`). The 75w carve-out stays `C/H/M/L`-only. A CWE class reference may still appear as a bare `[CWE-xxx]` bracket without the long form.
- **D-15:** `### Threat Patterns` stays REQUIRED-always (not omit-when-empty) -- analytical value-add; "No chaining -- findings independent" is meaningful; the fixture already asserts the header present and fails loudly if missing.

**Informational Cost-Control Guardrails**
- **D-16:** The executor never HUNTS for hardening -- `Informational` items are noted only opportunistically while triaging the real attack surface; "find hardening opportunities" is NEVER a Phase 1 scan goal.
- **D-17:** The advisor never spends tool-use turns (Read/Glob) VERIFYING Informational -- hardening notes are emitted from in-context material only.
- **D-18:** `Informational` is explicitly OPTIONAL, and a `<do_not_include>` item forbids manufacturing or padding hardening notes to fill the section.

## Summary

Phase 14.1 is a **pure prompt-content + fixture migration**, not a feature build. The work swaps the security-review output contract from the Conventional-Commits-derived `Critical / Important / Suggestions / Questions` taxonomy to the canonical pentest 5-tier scale `Critical / High / Medium / Low / Informational` plus a non-severity `Open Questions` section, scoped to **security-review only**. The companion `lz-review` / `reviewer` surfaces intentionally KEEP the old taxonomy -- Phase 14.1 is the deliberate vocabulary-divergence point that reverses the Phase 7 "unified lexicon" decision for security alone.

There is no external dependency, no runtime, no new package. The entire build is editing three files (`agents/security-reviewer.md`, `skills/lz-security-review/SKILL.md`, `tests/D-security-reviewer-budget.sh`), with two small doc touch-ups (ROADMAP goal text; an enum-divergence annotation in the shared `references/context-packaging.md`). The single dominant risk is **few-shot drift (WR-05 scar)**: Sonnet/Opus follow worked examples over stated rules, so the header list, the skeleton, ALL worked examples, the `<output_constraints>` block, the `<do_not_include>` items, and the fixture's self-extract source MUST change in ONE atomic commit or the agent emits a mixed vocabulary. The fixture (`D-security-reviewer-budget.sh`) self-extracts the holistic worked example from the agent file and budget-checks it -- so a stale example or a stale `SEV_HEADERS` regex fails the gate loudly, which is exactly the lockstep tripwire the planner should rely on.

The canonical naming was re-confirmed with observable web tools (FIRST.org CVSS v3.1 + v4.0 spec, OWASP Risk Rating Methodology, GitHub Advisory Database, multiple pentest-report guides, NIST SP 800-115): every major security ladder carries `Critical/High/Medium/Low` and an `Informational`/`Note`/observation tier listed SEPARATELY from key findings, validating D-01/D-02/D-06/D-12. One honest caveat: D-07's exact caveat wording is the user's locked phrasing (consistent with NIST SP 800-115's point-in-time / non-exhaustive / scope-bounded principle) but is NOT a verbatim NIST quote -- it does not need to be, since D-07 locks the literal string.

**Primary recommendation:** Plan it as ONE atomic lockstep plan (single commit) covering all three core surfaces + the two doc touch-ups, gated by the existing `D-security-reviewer-budget.sh` self-extract/self-test/`--from-trace` modes retargeted to the 5-tier grammar, with a closing `git status --porcelain` scope-fence proof that `reviewer.md` / `D-reviewer-budget.sh` / `lz-review` are byte-unchanged.

## Common Pitfalls

### Pitfall 1: Few-shot drift (WR-05 scar) -- the dominant risk
**What goes wrong:** The agent emits a MIXED vocabulary (some `### Important`, some `### High`) because the stated header list changed but a worked example still shows the old tier -- and LLMs follow worked examples over stated rules.
**Why it happens:** `[VERIFIED: .planning/STATE.md:164]` + `[VERIFIED: 14.1-CONTEXT.md code_context]` "LLMs follow worked examples over stated rules. The header list, the format/skeleton, ALL worked examples, the `<do_not_include>` items, and the fixture self-extract source must change in ONE atomic unit or output goes mixed."
**How to avoid:** Change ALL of these in one commit: S1 rows a-t (every header, skeleton, and worked example) + S3 rows a-g (fixture). The atomic unit is non-negotiable.
**Warning signs:** A `git grep -nE '### (Important|Suggestions|Questions)\b' -- plugins/lz-advisor/agents/security-reviewer.md` returns >0 after the edit; the fixture self-extract greens but a residue grep still finds old tokens.

### Pitfall 2: Stale self-extract source breaks the gate (intended tripwire)
**What goes wrong:** The fixture's `get_report` self-extracts the holistic example (S1 row l) and budget-checks it. If the holistic example is edited inconsistently (e.g. drops below 5 findings, or keeps a `(none)` line that the new `--self-test` no longer expects, or re-orders so it no longer opens with `### Critical`), the gate fails.
**Why it happens:** The fixture's `awk` range keys off `^> ### Critical$` as the start sentinel and the anti-vacuous guard needs `>=5` findings.
**How to avoid:** Author the new holistic example with `### Critical` as the FIRST section (D-05 order guarantees this when a Critical finding exists), >=5 findings, no `(none)` lines, and the new `SEV_HEADERS` tiers. This is a FEATURE -- the gate is the lockstep tripwire, not a bug.
**Warning signs:** "anti-vacuous: only N findings parsed (need >= 5)"; "agent file missing"; a self-extract that parses 0 findings.

### Pitfall 3: Informational + CVE bracket would wrongly claim the 75w escape (D-14)
**What goes wrong:** The fixture grants the 75w auto-clarity cap to ANY finding whose body carries `[CVE]/[GHSA]/[CWE]` -- regardless of section. D-14 denies Informational the 75w escape (hard 28w). A bracket-bearing Informational entry would pass the current fixture at up to 75w, violating D-14.
**Why it happens:** `[VERIFIED: tests/D-security-reviewer-budget.sh:235]` -- detection keys off the bracket alone, not the current section.
**How to avoid:** Make the budget loop section-aware: track `current_sev` through into `FINDING_BODIES` (e.g. parallel array), and when `current_sev == '### Informational'` force `cap=28` even if a bracket is present. The agent prose (D-14 + a `<do_not_include>` item) is the first line of defense; the fixture is the gate that makes it real.
**Warning signs:** A 40w Informational entry carrying a `[CWE-...]` bracket passing the gate.

### Pitfall 4: The shared `<verify_request>` schema is now a divergence point
**What goes wrong:** D-11 changes the security-reviewer's `severity=` enum but the schema is DEFINED in the shared `references/context-packaging.md` (L378, L390) which currently says "the same vocabulary for both reviewer and security-reviewer." Editing the shared enum to the new security vocabulary would silently break reviewer's contract; leaving it stale makes the shared doc lie.
**Why it happens:** `[VERIFIED: references/context-packaging.md:390]` the schema was authored as a single shared contract; Phase 14.1 forks it security-only.
**How to avoid:** In `context-packaging.md`, annotate the divergence: keep reviewer's `critical|important|suggestion`, add that security-reviewer uses `critical|high|medium|low|informational` (D-11). Do NOT change `reviewer.md:375`. This mirrors the Phase 12 "per-surface disposition table" discipline (`[VERIFIED: .planning/STATE.md:165]`).
**Warning signs:** `reviewer.md` or `D-reviewer-budget.sh` shows in `git status` (scope-fence breach).

### Pitfall 5: The "keep the two reviewer agents in sync" maintenance note becomes partly false (S1 row t)
**What goes wrong:** `security-reviewer.md:448` says the Hedge Marker Discipline section "is duplicated near-verbatim in the other reviewer agent ... keep the two in sync." After D-09, the security-clearance routing paragraph (L472) diverges (`Open Questions` vs reviewer's `Suggestions`). A future maintainer who "re-syncs" would re-introduce the old vocabulary.
**How to avoid:** Reword the maintenance note to scope the sync claim to the shared sentinel-pattern + frame paragraphs only, and explicitly flag the security-clearance routing paragraph as an INTENTIONAL divergence (Phase 14.1).
**Warning signs:** A later "sync the hedge sections" change reverts L472 to `### Suggestions`.

### Pitfall 6: Stale agent path in the fixture (carried-forward Phase-9 lesson)
**What goes wrong:** The fixture hardcodes `SECURITY_AGENT="plugins/lz-advisor/agents/security-reviewer.md"`. A wrong path yields a silent vacuous pass.
**Why it happens:** `[VERIFIED: tests/D-security-reviewer-budget.sh:42,80-86]` -- already guarded with a loud-fail existence check. No path change this phase (no `git mv`), so this is LOW risk; noted only so the planner does not accidentally move the agent file.
