## Summary

This plan adds a SECOND committed workflow, `.github/workflows/test-act.yml`, that installs a pinned `nektos/act` and runs it against the repo's own `ci.yml` inside a GitHub-hosted `ubuntu-latest` runner. It is "meta-CI": it does not test the aggregator (that is `ci.yml`'s job, run natively); it tests that `ci.yml` is still RUNNABLE under act -- catching act-compatibility drift in the workflow's structure, action pins, and the `node --test` command. The redundancy is accepted and documented (D-13).

Every load-bearing fact was VERIFIED this session, several by running `act` against the real `ci.yml` on the local host (act 0.2.84, Docker 29.4.0). The decisive findings: (1) GitHub-hosted `ubuntu-latest` ships Docker with the daemon already running and passwordless sudo, so act needs no Docker setup step `[VERIFIED: GitHub docs]`; (2) act's `--list` lists jobs WITHOUT pulling an image, but on a FRESH host (no `~/.actrc`) ANY act run -- including `-n` -- BLOCKS on an interactive "choose image size" prompt and fails non-interactively (`level=fatal msg="Incorrect function."`, exit 1) `[VERIFIED: local run]`; the workflow MUST pass an explicit `-P ubuntu-latest=<image>` (or pre-seed `~/.actrc`) on every act invocation; (3) with `-P`, `act -n push -j test -W .github/workflows/ci.yml` dry-runs the entire ci.yml step graph and exits 0 `[VERIFIED: local run]`; (4) act fetches the SHA-pinned `actions/checkout`+`actions/setup-node` by `git clone` from github.com, so a real run needs `-s GITHUB_TOKEN=${{ github.token }}` to avoid anonymous rate-limiting `[VERIFIED: dry-run trace + nektos/act docs]`; (5) `actions/checkout` is a NO-OP under act by default (act copies the workdir in), which is fine here -- the test job only needs the repo present, not a real clone `[CITED: nektos/act docs]`.

**Primary recommendation:** One job `act` on `ubuntu-latest`, `permissions: contents: read`, same concurrency block as ci.yml. Steps: (1) `actions/checkout@<SHA>` (to get `ci.yml` + `.node-version` + the tests into the runner workspace); (2) a `run:` step that downloads `act_Linux_x86_64.tar.gz` for a PINNED version (0.2.89), verifies it against the release `checksums.txt` with `sha256sum -c`, and extracts the `act` binary to a workspace-local path; (3) a `run:` step that executes, in order, `act --list -W .github/workflows/ci.yml`, then `act -n push -j test -W .github/workflows/ci.yml -P ubuntu-latest=catthehacker/ubuntu:act-22.04`, then the REAL `act push -j test -W .github/workflows/ci.yml -P ubuntu-latest=catthehacker/ubuntu:act-22.04 -s GITHUB_TOKEN=${{ github.token }}`. Set `timeout-minutes: 20` to absorb the image pull. ASCII-only throughout.

### Pattern 1: pinned-act-in-a-runner with explicit -P on every invocation
**What:** Install a pinned act, then run `--list`/`-n`/real with an EXPLICIT `-P ubuntu-latest=<image>` so act never hits the interactive image-size prompt.
**When to use:** Any non-interactive (CI) act invocation on a fresh host with no `~/.actrc`.
**Example (synthesized; SHAs/version re-resolved at write time):**
```yaml
# Source: synthesized from nektosact.com (runners, GITHUB_TOKEN), GitHub docs (ubuntu-latest Docker),
# and LOCAL act runs this session against the real ci.yml. ASCII-only.
name: test-act

on:
  workflow_dispatch:
  push:
    branches: [main]
    paths:
      - .github/workflows/ci.yml
      - .github/workflows/test-act.yml
      - .node-version
      - plugins/lz-advisor/skills/**/*.test.mjs
      - plugins/lz-advisor/skills/**/scripts/*.mjs
  pull_request:
    branches: [main]
    paths:
      - .github/workflows/ci.yml
      - .github/workflows/test-act.yml
      - .node-version
      - plugins/lz-advisor/skills/**/*.test.mjs
      - plugins/lz-advisor/skills/**/scripts/*.mjs

concurrency:
  group: ${{ github.workflow }}-${{ github.ref }}
  cancel-in-progress: true

permissions:
  contents: read

jobs:
  act:
    runs-on: ubuntu-latest
    timeout-minutes: 20
    env:
      ACT_VERSION: 0.2.89
      ACT_IMAGE: catthehacker/ubuntu:act-22.04   # pin a dated tag or digest at write time (Q3)
    steps:
      - uses: actions/checkout@df4cb1c069e1874edd31b4311f1884172cec0e10 # v6.0.3

      - name: Install and verify act (pinned release + checksum)
        run: |
          set -euo pipefail
          base="https://github.com/nektos/act/releases/download/v${ACT_VERSION}"
          curl -fsSL -o act.tar.gz "${base}/act_Linux_x86_64.tar.gz"
          curl -fsSL -o checksums.txt "${base}/checksums.txt"
          sha256sum --ignore-missing -c checksums.txt
          tar -xzf act.tar.gz act
          ./act --version

      - name: act structure + dry-run + real run against ci.yml
        env:
          GH_TOKEN_FOR_ACT: ${{ github.token }}
        run: |
          set -euo pipefail
          ./act --list -W .github/workflows/ci.yml
          ./act -n push -j test -W .github/workflows/ci.yml -P "ubuntu-latest=${ACT_IMAGE}"
          ./act push -j test -W .github/workflows/ci.yml \
            -P "ubuntu-latest=${ACT_IMAGE}" \
            -s GITHUB_TOKEN="${GH_TOKEN_FOR_ACT}"
```
Notes:
- The `-P` mapping is REQUIRED on `-n` and the real run (NOT strictly on `--list`, but harmless to include) -- without it, a fresh runner with no `~/.actrc` triggers the interactive prompt and `act` exits 1. `[VERIFIED: local run, "Incorrect function." fatal]`
- `--ignore-missing` makes `sha256sum -c` check ONLY the file we downloaded against the multi-line `checksums.txt`, ignoring the other-platform lines. `[VERIFIED: checksums.txt is GNU format]`
- Passing the token via an `env:` indirection (`GH_TOKEN_FOR_ACT`) and then `-s GITHUB_TOKEN="${GH_TOKEN_FOR_ACT}"` keeps the secret out of the `run:` argv literal in logs; `${{ github.token }}` is the workflow's own read-only token. `contents: read` is sufficient for cloning PUBLIC first-party actions.

### Anti-Patterns to Avoid
- **Omitting `-P` on a fresh runner:** triggers the interactive image-size prompt; the job hangs/fails. ALWAYS pass `-P ubuntu-latest=<image>`. `[VERIFIED]`
- **Unpinned `curl | bash` install:** violates D-13. Use the pinned tarball + checksum.
- **Using the host/local act:** the local 0.2.84 is CVE-vulnerable; the workflow installs its OWN pinned 0.2.89 anyway (the runner has no act preinstalled).
- **`:full-latest` (Large) image:** ~17GB download; exceeds the runner disk + the 20-min budget. Use Medium (`:act-*`).
- **`docker:dind` / nested Docker setup step:** unnecessary -- the GitHub-hosted runner already has Docker; act talks to the host daemon directly.
- **Mutable `:act-latest` for long-term reproducibility:** acceptable for v1 but a DATED tag or digest is more reproducible (Q3).
- **Treating this as a coverage/test gate:** it is NOT -- ci.yml owns that natively. This is an act-compatibility gate (D-13 redundancy caveat).

## Common Pitfalls

### Pitfall 1: Fresh-runner interactive image-size prompt blocks act (HIGH impact)
**What goes wrong:** On a runner with no `~/.actrc`, the FIRST act invocation that needs an image (including `act -n`) prints "Please choose the default image you want to use with act" and, non-interactively, dies with `level=fatal msg="Incorrect function."` exit 1.
**Why it matters here:** Every CI run starts on a fresh runner with no `~/.actrc`. Without mitigation the job fails before testing anything.
**How to avoid:** Pass `-P ubuntu-latest=<image>` on the `-n` and real invocations (the proven fix this session). Alternatively, write `~/.actrc` (or `$XDG_CONFIG_HOME/act/actrc`) with the `-P` line before invoking. `--list` does NOT need it but include it for uniformity.
**Warning signs:** `Incorrect function.` fatal, or a hung step. `[VERIFIED: local run 2026-06-16]`

### Pitfall 2: act needs a Docker daemon connection even for `-n` (but NOT an image pull)
**What goes wrong:** `act -n` and even `--list` log the docker host and connect to the daemon; on a host with no daemon they error "Cannot connect to the Docker daemon".
**Why it matters here:** NON-issue on GitHub-hosted ubuntu-latest -- Docker is preinstalled and the daemon is running with passwordless sudo. No Docker-setup step needed. `--list` connects but does NOT pull an image; `-n` plans without pulling; only the REAL run pulls.
**How to avoid:** Nothing required on ubuntu-latest. (Do NOT add a `docker` setup action -- redundant.) `[VERIFIED: GitHub docs ubuntu-latest Docker preinstalled; local --list/-n connected without pulling]`
**Warning signs:** "Cannot connect to the Docker daemon" -- would only appear if someone switched to `ubuntu-slim` (unprivileged, no DinD) or a self-hosted runner without Docker.

### Pitfall 3: act 0.2.84 (and earlier) is CVE-vulnerable (CVE-2026-34041 / CVE-2026-34042)
**What goes wrong:** act < 0.2.86 self-reports two CVEs ("please upgrade to 0.2.86 or later").
**Why it matters here:** D-13 mandates a pinned install. Pin a SAFE version.
**How to avoid:** Pin `ACT_VERSION=0.2.89` (latest, well past the 0.2.86 fix). Re-check the latest patch at write time and never pin below 0.2.86. `[VERIFIED: local act 0.2.84 stderr emitted the CVE warning this session]`
**Warning signs:** A red CVE banner in the act stderr; a pinned version < 0.2.86.

### Pitfall 4: act needs GITHUB_TOKEN to fetch the SHA-pinned actions without rate-limiting
**What goes wrong:** act clones `actions/checkout` and `actions/setup-node` (by their pinned SHAs) from github.com via `git clone`. Anonymous clones hit GitHub's unauthenticated rate limit; a missing token can also surface "Input required and not supplied: token" for actions that read the token.
**Why it matters here:** The real run fetches both SHA-pinned actions; on a busy runner IP the anonymous limit can bite.
**How to avoid:** Pass `-s GITHUB_TOKEN=${{ github.token }}`. The workflow's own token is read-only (`contents: read`) and sufficient to clone PUBLIC first-party actions. Do NOT mint a PAT. CAVEAT (nektos/act docs): a deliberately FAKE token can make act FAIL when it tries to clone with it -- use the REAL `${{ github.token }}`, not a placeholder.
**Warning signs:** "API rate limit exceeded" or "Input required and not supplied: token" during the action-fetch phase. `[VERIFIED: dry-run trace showed `git clone 'https://github.com/actions/setup-node' # ref=<SHA>`; CITED: nektosact.com GITHUB_TOKEN docs]`

### Pitfall 5: setup-node resolving `lts/krypton` needs network inside the act container
**What goes wrong:** Inside the act container, `actions/setup-node` resolves `lts/krypton` against its bundled manifest and downloads Node 24 from the Node dist server -- this requires outbound network from the container.
**Why it matters here:** The act container uses `network="host"` by default (seen in the dry-run trace: `docker run ... network="host"`), so it inherits the runner's network -- network IS available. The Medium catthehacker image is built to bootstrap setup-node. Risk is low but the inner run is where `lts/krypton` resolution is actually exercised under act.
**How to avoid:** Use the Medium image (NOT Micro). The host-network default gives outbound access. If `lts/krypton` ever fails to resolve in the container's bundled setup-node manifest, the same fallback ladder as 17.3-RESEARCH.md Pitfall 2 applies -- but that is a ci.yml concern, not a test-act.yml concern. `[VERIFIED: dry-run trace network=host; setup-node SHA is v6.4.0, current]`

### Pitfall 6: The multi-GB image pull dominates run time; caching it is usually not worth it
**What goes wrong:** The real run pulls the catthehacker Medium image (~500MB compressed, more extracted) on every run; act's `--pull` defaults to true (force-pulls each run).
**Why it matters here:** Pull time + extraction can take several minutes; without a `timeout-minutes` the job could hit the default 6-hour cap only after a hang, or fail opaquely.
**How to avoid:** Set `timeout-minutes: 20` on the job (generous headroom for pull + run). Caching the Docker image via `actions/cache` (save/load a `docker save` tarball) is generally NOT worth the complexity for a narrowly-triggered workflow (D-12) that runs rarely -- KEEP IT SIMPLE. The D-12 paths-filter is the right cost-control mechanism, not image caching. `[CITED: nektosact runners docs (--pull default true); image-size figures from local act prompt]`
**Warning signs:** Job timing out; repeated full pulls on a hot path (mitigated by D-12's narrow triggers).

### Pitfall 7: A SHA pin can come from a malicious fork (inherited from 17.3-RESEARCH.md Pitfall 4)
**What goes wrong:** A valid SHA does not prove the commit belongs to the upstream repo.
**Why it matters here:** test-act.yml reuses the ci.yml `actions/checkout` SHA.
**How to avoid:** Re-resolve `actions/checkout` from the UPSTREAM repo tags at write time (`git ls-remote --tags https://github.com/actions/checkout.git`), keep the `# v6.0.3` comment, and keep `permissions: contents: read`. `[CITED: 17.3-RESEARCH.md Pitfall 4]`

## Validation Architecture

> nyquist_validation is not explicitly disabled, so this section is included. CRITICAL: the deliverable is a YAML workflow whose PURPOSE is to run another workflow under act. There is a nesting trap -- see below.

### The nesting trap (why you cannot "act the test-act workflow" locally)
Running `act` against `test-act.yml` locally would mean act-inside-act-inside-Docker (the inner act would try to launch a Docker container from within an act container without a daemon). This is meaningless and will not work. **Do NOT validate test-act.yml by running `act -W test-act.yml`.** The real validations are:
1. **Local proof the INNER command works:** run `act push -j test -W .github/workflows/ci.yml -P ubuntu-latest=catthehacker/ubuntu:act-22.04 -s GITHUB_TOKEN="$(gh auth token)"` on the dev host (Docker + act present). If ci.yml passes under act locally, the same invocation in test-act.yml will pass on the runner. This session ALREADY proved the dry-run (`act -n push ...`) exits 0 against the real ci.yml; the real run is the remaining local proof.
2. **Workflow runs green on GitHub:** push the branch and confirm the `test-act` workflow's `act` job goes green (the only authoritative end-to-end signal -- it exercises the real runner's Docker, the pinned act install + checksum, the image pull, and the token-authed action fetch).
3. **Static lint (optional, complementary):** `actionlint .github/workflows/test-act.yml` (and ci.yml) catches YAML/expression errors before the heavier act run. NOT a substitute for the act run (D-11 chose act as primary).
