<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| third-party action -> CI runner | `actions/checkout` and `actions/setup-node` execute in the workflow with the job's GITHUB_TOKEN; a compromised/forked action runs in our context |
| PR author -> CI workflow | a `pull_request` from a fork triggers the workflow; untrusted PR-controlled content must not gain write privileges |
| GITHUB_TOKEN -> repo | the default token's scope is the blast radius if the runner or an action is compromised |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-17.3-01 | Tampering / Elevation | third-party action pinning in ci.yml | mitigate | Pin `actions/checkout` and `actions/setup-node` to full immutable upstream commit SHAs (Task 3 + Task 4 acceptance criteria), NOT floating `@v6` tags; trailing `# vX.Y.Z` comment for review |
| T-17.3-02 | Spoofing / Tampering | malicious-fork SHA (valid SHA, wrong repo) | mitigate | Verify each chosen SHA appears in `git ls-remote --tags` for the CORRECT upstream repo before pinning (Task 3; 2026 Trivy fork-SHA incident) |
| T-17.3-03 | Elevation | GITHUB_TOKEN scope | mitigate | Top-level `permissions: contents: read` only, no job-level escalation (D-09, Task 4 acceptance criterion) |
| T-17.3-04 | Elevation | PR-injection via writable token | mitigate | Use plain `pull_request` (read-only context), NEVER `pull_request_target`; no shell step interpolates untrusted PR-controlled values (Task 4) |
| T-17.3-05 | Tampering | mutable-tag swap (tag moved to a malicious commit) | mitigate | SHA pin instead of `@vN` floating tag closes the moved-tag vector (T-17.3-01 mitigation) |
| T-17.3-SC | Tampering | npm/pip/cargo installs | accept | No package-manager installs in this phase -- there is NO package.json and the workflow runs `node --test` directly with zero install steps (RESEARCH Package Legitimacy Audit: slopcheck N/A, no registry package names). No `[ASSUMED]`/`[SUS]` packages exist, so no legitimacy checkpoint is required. |
</threat_model>
