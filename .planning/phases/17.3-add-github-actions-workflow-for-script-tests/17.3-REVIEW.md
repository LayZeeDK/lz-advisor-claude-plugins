# Phase 17.3: Code Review Report

**Reviewed:** 2026-06-16

## Summary

Reviewed the Phase 17.3 GitHub Actions CI surface: `ci.yml` (node --test with a fail-closed
coverage gate), `test-act.yml` (meta-CI running nektos/act against ci.yml), `.actrc` (pinned act
runner image), and `.node-version` (Node LTS pin). The workflows follow strong supply-chain
hygiene: actions are pinned to peeled commit SHAs with version comments, act is pinned to a
release version with sha256 checksum verification, `permissions` is set to least-privilege
`contents: read`, and the GITHUB_TOKEN is passed via an intermediate env var (injection-safe)
rather than direct `${{ }}` interpolation into a shell. No critical defects found.

Two warnings concern an untrusted-code-execution exposure inherent to the meta-CI's real `act`
run on fork pull requests, and a latent gap in the checksum-verification command. Two info items
note minor robustness improvements. The pre-noted intentional decisions (SHA pinning, image
sync, least-privilege, ASCII-only) were verified and are NOT re-flagged.

## Warnings

### WR-01: Fork PR can execute attacker-controlled test code via real `act` run

**File:** `.github/workflows/test-act.yml:14-22, 53-62`
**Issue:** `test-act.yml` triggers on `pull_request` with a `paths` filter that explicitly
includes `plugins/lz-advisor/skills/**/*.test.mjs` and `plugins/lz-advisor/skills/**/scripts/*.mjs`.
The job then performs a REAL run (`./act push -j test ...`, not just `-n`/dry-run), which executes
`node --test` against those very files. A pull request from a fork that edits a `.test.mjs` or a
`scripts/*.mjs` file therefore runs attacker-controlled JavaScript on the runner. This is mitigated
correctly -- it is `pull_request` (not `pull_request_target`), so the workflow runs with the
read-only fork token and no repository secrets, and `permissions: contents: read` further limits
blast radius -- so it is NOT a critical secret-exfiltration vector. But the runner still executes
untrusted code, which can consume CI minutes, attempt egress, or probe the runner. This is the
accepted GitHub model, but it should be a conscious, documented decision.
**Fix:** If executing untrusted PR code on this runner is not intended, gate the real run behind a
trust check or restrict the meta-CI to `push` / `workflow_dispatch` only and keep `pull_request`
limited to a dry-run (`-n`). For example, skip the real-run step on fork PRs:
```yaml
      - name: act structure + dry-run + real run against ci.yml
        if: github.event_name != 'pull_request' || github.event.pull_request.head.repo.full_name == github.repository
```
(keep an unconditional `-n` dry-run step for fork PRs). If untrusted execution is intended, add a
comment at the trigger documenting that fork test code is deliberately executed under the read-only
token.

### WR-02: Checksum verification can silently pass if upstream renames the release asset

**File:** `.github/workflows/test-act.yml:47-50`
**Issue:** `sha256sum --ignore-missing -c checksums.txt` verifies only those entries in
`checksums.txt` whose named file is present on disk. The pipeline downloads
`act_Linux_x86_64.tar.gz` and then verifies. If a future `act` release renames or restructures the
Linux x86_64 asset (so the on-disk name no longer matches any line in `checksums.txt`),
`--ignore-missing` skips it. GNU coreutils does exit non-zero when zero files match (no file was
verified), so a total mismatch fails closed -- but there is no explicit assertion that the SPECIFIC
artifact we extracted was the one verified. The integrity guarantee is implicit and depends on
coreutils' "no file verified" behavior remaining stable.
**Fix:** Verify the exact downloaded artifact explicitly so the check cannot be silently bypassed:
```bash
grep " act_Linux_x86_64.tar.gz$" checksums.txt | sha256sum -c -
```
This fails loudly if the expected line is absent, rather than relying on `--ignore-missing`
semantics.

## Info

### IN-01: `act --version` output is not asserted against `ACT_VERSION`

**File:** `.github/workflows/test-act.yml:51`
**Issue:** `./act --version` is run for visibility but its output is not compared to
`${ACT_VERSION}`. The download URL embeds the version, so a wrong binary is unlikely, but an
explicit assertion would catch a checksum-file/tarball version skew.
**Fix:** Optionally assert the version, e.g. `./act --version | grep -q "${ACT_VERSION}"`.

### IN-02: No `defaults.run.shell` / fail-fast hardening at workflow level

**File:** `.github/workflows/test-act.yml:44-62`
**Issue:** Each `run:` block already sets `set -euo pipefail`, which is good. This is duplicated
across both multi-line steps; a workflow-level `defaults: { run: { shell: bash } }` plus the
per-step pipefail is fine as-is. Purely a consistency note -- no defect.
**Fix:** None required; leave as-is or hoist a shared default if more shell steps are added later.
