# Phase 17.3 Plan 02 (CI-06): act meta-CI workflow Summary

A committed `.github/workflows/test-act.yml` installs a pinned, checksum-verified nektos/act 0.2.89 and runs it against the repo's own `ci.yml` inside ubuntu-latest, backed by a repo-root `.actrc` that single-sources the pinned runner-image `-P` default to defuse act's interactive image-size prompt.

## What was built

**`.actrc` (repo root):** One `-P ubuntu-latest=catthehacker/ubuntu:act-22.04` line plus an ASCII comment documenting it as the single-source image pin (D-13) and noting the stricter `@sha256:<digest>` form. The runner checks out the repo and runs act from the workspace root, so this same file is honored on the runner -- a bare `act --list` / `act -n` no longer hits the interactive image-size prompt (research landmine 1).

**`.github/workflows/test-act.yml`:** `name: test-act`, single job `act` on `ubuntu-latest`, `timeout-minutes: 20`.
- Triggers (D-12): `workflow_dispatch` + paths-filtered `push`/`pull_request` to `[main]` covering `.actrc`, `.github/workflows/ci.yml`, `.github/workflows/test-act.yml`, `.node-version`, `plugins/lz-advisor/skills/**/*.test.mjs`, `plugins/lz-advisor/skills/**/scripts/*.mjs`.
- `concurrency: ${{ github.workflow }}-${{ github.ref }}` + `cancel-in-progress: true` (verbatim from ci.yml, D-11).
- `permissions: contents: read` only, top-level (D-11).
- `env: ACT_VERSION: 0.2.89`, `ACT_IMAGE: catthehacker/ubuntu:act-22.04` (byte-identical to `.actrc` -- no drift).
- Step 1: `actions/checkout@df4cb1c069e1874edd31b4311f1884172cec0e10 # v6.0.3` (SHA-pinned, reuses ci.yml's pin, D-13).
- Step 2: install act -- `curl` the v0.2.89 `act_Linux_x86_64.tar.gz` + `checksums.txt`, `sha256sum --ignore-missing -c checksums.txt` (fails non-zero on mismatch, D-13/CI-06c), `tar -xzf`, `./act --version`. No hardcoded hex.
- Step 3: three act invocations in order against ci.yml -- `./act --list`, `./act -n push -j test ... -P "ubuntu-latest=${ACT_IMAGE}"` (dry-run), then the real `./act push -j test -W .github/workflows/ci.yml -P "ubuntu-latest=${ACT_IMAGE}" -s GITHUB_TOKEN="${GH_TOKEN_FOR_ACT}"`. Token sourced from `${{ github.token }}` via a step `env` indirection (kept out of argv).
- No `docker/setup-*`, no `services:`, no DinD (ubuntu-latest ships Docker, research Pitfall 2/5).

## Task 2 disposition: A1 full inner-run DEFERRED to the GitHub-side green run

The nesting trap was avoided -- act was NOT run against `test-act.yml`; the local proof targets `ci.yml`.

The full local inner act run is **explicitly DEFERRED to the GitHub-side green run** of the `test-act` workflow. Rationale: the only act available on this dev host is 0.2.84 (standalone binary AND the `gh act` extension), which self-reports CVE-2026-34041 / CVE-2026-34042 and is below the 0.2.86 floor the plan and threat register (T-17.3-02-02) require for the local proof. Per the plan's Task 2 disposition and phase-specific guidance landmine 9, a vulnerable/old act must NOT be run; an upgrade to >= 0.2.86 could not be cleanly obtained in this environment without a network install. Running the CVE binary -- even the cheap bare `act --list` prompt-defusion check -- was therefore refused. The workflow installs its OWN pinned 0.2.89 regardless, so the runner never uses the local 0.2.84.

Proven status carried from the research session (HIGH confidence): the dry-run `act -n push -j test -W .github/workflows/ci.yml -P ubuntu-latest=catthehacker/ubuntu:act-22.04` exited 0 against the real ci.yml, tracing checkout / setup-node / `node --test` with `network="host"` and the SHA-pinned action clones.

**A1 (setup-node resolving `lts/krypton` end-to-end inside the act container) remains OPEN until the first CI run.** No image change was needed (the dry-run was green), so `.actrc` and `ACT_IMAGE` stay at `catthehacker/ubuntu:act-22.04` with zero drift. The authoritative end-to-end signal -- to be recorded in VALIDATION.md -- is the `test-act` workflow going green on the PR branch: it exercises the runner's Docker, the pinned act install + checksum, the .actrc-honored image pin, the image pull within the 20-minute timeout, the token-authed action fetch, and the inner ci.yml run end-to-end.

## Threat model compliance

All mitigate-disposition threats from the plan's `<threat_model>` are implemented:

## Post-Review Refinement (code review + user-directed event parity)

Three follow-ups after the `/gsd-code-review` pass and an interactive decision round (commit `bc1774a`):

- **pull_request parity (user-directed):** the act step now simulates BOTH `act push` AND
  `act pull_request` against `ci.yml` (dry-run + real run for each), matching ci.yml's own
  `push:main` + `pull_request:main` triggers. The `test` job is event-agnostic so this is literal
  trigger parity, not differing behavior. Both events proven green locally
  (`pull_request` full run: lts/krypton -> v24.14.0, 39 pass, 97.84/89.57/100, Job succeeded).
- **WR-02 (review warning):** checksum verification pinned to the exact asset line
  (`grep ' act_Linux_x86_64.tar.gz$' checksums.txt | sha256sum -c -`) instead of
  `--ignore-missing -c`.
- **Checksum asset-filename bug (caught by local validation, pre-existing):** the install step
  downloaded the tarball as `act.tar.gz` while `checksums.txt` names it `act_Linux_x86_64.tar.gz`,
  so `sha256sum -c` could never find the file (the original `--ignore-missing` form would have
  failed on the runner with "no file was verified"). Fixed to download + extract under the canonical
  `act_Linux_x86_64.tar.gz` name. Verified locally end-to-end: `act_Linux_x86_64.tar.gz: OK`, exit 0.
  This is exactly the class of defect the meta-CI exists to catch -- surfaced here by running the
  real download+verify locally rather than deferring it.

WR-01 (fork-PR guard) was deliberately NOT added: with plain `pull_request` (read-only token, no
secrets) and `ci.yml` already running PR test code natively, it provides no security benefit.
