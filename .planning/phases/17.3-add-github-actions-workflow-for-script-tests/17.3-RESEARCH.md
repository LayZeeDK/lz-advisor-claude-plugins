## Summary

This phase stands up a single GitHub Actions workflow (`.github/workflows/ci.yml`) and a root `.node-version` file for a repo whose ONLY executable code is one zero-dependency Node ESM script (`lz-deep-research-aggregate.mjs`, 739 LOC) plus its `node:test` suite (951 LOC, 39 `test()` declarations). There is no root `package.json`, and the zero-dependency ethos is load-bearing -- so every CONTEXT decision (built-in coverage only, no c8/istanbul, no `npm ci` step) is both correct and forced by the repo shape.

Every load-bearing fact is verifiable against current authoritative sources as of 2026-06-16. The current Active LTS line is **Node 24, codename Krypton** (`lts/krypton`), entered Active LTS 2025-10-28; the local dev machine already runs v24.13.0. Node's built-in test coverage (`--experimental-test-coverage`, still Stability-1 Experimental in Node 24) reports **line / branch / function only -- no MC/DC, no per-operator coverage** -- and the threshold flags `--test-coverage-lines/-branches/-functions` **exit the process with code 1** when coverage is below threshold (the fail-closed gate D-02 wants). This confirms D-04: MC/DC and `??`/`?.` operator coverage are genuinely infeasible with zero-dep tooling, not a preference.

**Primary recommendation:** Single workflow, single `test` job on `ubuntu-latest`: `checkout` -> `setup-node` (with `node-version-file: .node-version`) -> one `run:` step `node --test --experimental-test-coverage --test-coverage-lines=100 --test-coverage-branches=100 --test-coverage-functions=100 "plugins/lz-advisor/skills/**/*.test.mjs"` (exact threshold numbers per the D-03 measurement run). Pin `actions/checkout` and `actions/setup-node` to **full commit SHAs with a trailing version comment** (current OpenSSF/GitHub recommendation, now org-enforceable). The CLI bootstrap guard (`if (import.meta.url === ...) main()`, source lines ~721-739) is the only unreachable region under the test process -- wrap it in `/* node:coverage disable */` / `/* node:coverage enable */` so the 100% global gate stays honest. ONE real risk to flag to the planner: a newly-promoted LTS codename can fail to resolve in an OLD setup-node manifest (historical `lts/jod` issue #1154); mitigate by pinning a CURRENT setup-node major (v6), and verify resolution on the first CI run.

### Pattern 1: Single-job, no-install, glob-discovery test workflow
**What:** One `test` job; no `npm ci` (no package.json); discovery via an explicit double-quoted glob.
**When to use:** Zero-dependency Node repos whose tests use the built-in runner.
**Example:**
```yaml
# Source: synthesized from nodejs.org/docs/latest-v24.x/api/test.html (glob + coverage flags)
#         and github.com/actions/setup-node README (node-version-file). Exact SHAs/thresholds
#         finalized in planning per D-03.
name: CI

on:
  push:
    branches: [main]
  pull_request:
    branches: [main]

concurrency:
  group: ${{ github.workflow }}-${{ github.ref }}
  cancel-in-progress: true

permissions:
  contents: read

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@<full-sha>   # v6.0.x
      - uses: actions/setup-node@<full-sha> # v6.x
        with:
          node-version-file: .node-version
      - run: >
          node --test --experimental-test-coverage
          --test-coverage-lines=100
          --test-coverage-branches=100
          --test-coverage-functions=100
          "plugins/lz-advisor/skills/**/*.test.mjs"
```
Notes:
- The glob MUST be double-quoted so the shell does not expand it -- Node's runner does the glob expansion itself (glob(7) semantics). `[VERIFIED: nodejs.org test runner docs]`
- `>` folded scalar keeps the long `node` command readable; a single-line `run:` is equally valid.

### Anti-Patterns to Avoid
- **`npm ci` / `npm install` step:** there is no `package.json` -- the step would fail. Run `node --test` directly.
- **Bare directory argument (`node --test plugins/...`):** D-05 forbids it; use the glob. (The bare-dir spurious-exit-1 is a local Windows-arm64 quirk, but the glob is the intention-revealing CI form regardless.)
- **`pull_request_target`:** never use it here -- it runs with a writable token in the BASE repo context and is the classic PR-injection vector. Plain `pull_request` (read-only, D-09) is correct.
- **Mutable tag pins (`@v6`) for the long term:** acceptable for first-party actions but the current OpenSSF/GitHub recommendation is full-SHA pins (see Pitfall 4).
- **Mixing the two coverage gates with a wrong assumption about events:** see Pitfall 1 (threshold breach exits non-zero but historically did NOT emit `test:fail` -- harmless for a CLI gate, but do not build event-based logic on it).

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Coverage measurement | A custom V8 coverage parser | `--experimental-test-coverage` | Built into Node; zero deps |
| Coverage threshold gate | A grep over coverage output + manual `exit 1` | `--test-coverage-lines/-branches/-functions=N` | Built-in, fails the process at code 1 |

## Common Pitfalls

### Pitfall 1: Coverage threshold breach exits non-zero but does NOT emit `test:fail` (historical Node bug)
**What goes wrong:** A reporter/event-based assumption ("a coverage failure emits a `test:fail` event") is wrong on some Node versions (nodejs/node#54812): the threshold breach prints a `test:diagnostic` like `Error: 82.35% function coverage does not meet a threshold of 95%` AND **sets a non-zero exit code**, but historically did not emit `test:fail`.
**Why it matters here:** It does NOT matter for this CI -- the workflow gates on the PROCESS EXIT CODE (`run:` step fails the job on non-zero exit), which IS set. The `--test-coverage-*` docs explicitly state "the process will exit with code 1" below threshold.
**How to avoid:** Gate on exit code (the default `run:` behavior). Do NOT build a custom reporter that keys off `test:fail` for coverage. `[CITED: github.com/nodejs/node/issues/54812; nodejs.org test runner docs]`
**Warning signs:** A green job despite an obvious coverage miss -- would only happen if someone added `|| true` or a reporter swallowing the exit.

### Pitfall 2: A newly-promoted LTS codename fails to resolve in an OLD setup-node manifest
**What goes wrong:** `setup-node` resolves `lts/<codename>` against a manifest BUNDLED in the action version. A codename promoted after that action build errors: `Unable to find LTS release '<codename>' for Node version 'lts/<codename>'` (exactly what happened for `lts/jod` -- issue #1154).
**Why it matters here:** `lts/krypton` is relatively new (Krypton promoted 2025-10-28). An old setup-node major could fail to resolve it.
**How to avoid:** Pin a CURRENT setup-node major (v6, latest v6.4.0 Apr 2026 -- well past Krypton's promotion). VERIFY resolution on the first CI run. **Fallback ladder if it ever fails:** (1) bump setup-node to the latest patch; (2) use `node-version-file` with `lts/*` (resolves to the latest LTS = Krypton today); (3) explicit `node-version: '24'`. The roadmap LOCKS the `lts/<codename>` FILE format (D-06), so prefer keeping the file as `lts/krypton` and adjusting only the action version. `[VERIFIED: setup-node issue #1154; v6.4.0 release date]`
**Warning signs:** First CI run red at the setup-node step with an "Unable to find LTS release" message.

### Pitfall 3: `??` site is exercised, but confirm under BRANCH coverage
**What goes wrong:** D-03 targets 100% branch coverage; the source has exactly ONE `??` site -- `.map((w) => NUMWORDS[w] ?? w)` (line 75). Its left operand is `undefined` only when a token is NOT a number-word. If every fixture token were a number-word (it isn't), the `?? w` right branch could be uncovered.
**Why it matters here:** Branch coverage at 100% requires both arms of the `??` taken. Ordinary text fixtures (which contain non-number-words) take the `?? w` arm; number-word fixtures take the left arm. The 39-test suite almost certainly exercises both, but D-03's measurement run is where this is CONFIRMED.
**How to avoid:** The one-time measurement run (D-03) reports the achieved branch %. If branch < 100% solely due to the `??` site, add one trivial assertion exercising both arms (Claude's-discretion item in CONTEXT). `[VERIFIED: git grep -- 1x ?? at line 75, 0x ?. confirmed this session]`
**Warning signs:** Branch coverage stuck just below 100% with the uncovered region pointing at `normalize()`.

### Pitfall 4: SHA pins can come from a malicious fork (2026 Trivy incident)
**What goes wrong:** A full-SHA pin is immutable but a valid SHA does NOT prove the commit belongs to the upstream repo -- an orphaned commit in a fork has a valid SHA (March 2026 Trivy/`actions/checkout` fork-visibility incident).
**Why it matters here:** Even first-party `actions/*` pins should be verified against the upstream tag.
**How to avoid:** Resolve the SHA from the UPSTREAM repo's tags (`git ls-remote --tags https://github.com/actions/checkout.git`) -- which is exactly how the SHAs in the audit above were obtained -- and keep the `# vX.Y.Z` comment so reviewers can cross-check. Pair SHA-pinning with least-privilege `permissions: contents: read` (D-09) so a compromised action's blast radius is read-only. `[CITED: GitHub Docs secure-use; OpenSSF Scorecard; vaines.org / rosesecurity.dev Trivy writeups, Mar 2026]`
**Warning signs:** A SHA that does not appear in `git ls-remote --tags` output for the upstream repo.

### Pitfall 5: Double-run from both `push` and `pull_request`
**What goes wrong:** Configuring `push` on all branches PLUS `pull_request` makes a PR branch's push fire BOTH events -> two runs.
**Why it matters here:** D-07 already solves it: `push` is scoped to `branches: [main]` only; PRs validate via `pull_request`. Keep that scoping.
**How to avoid:** `on.push.branches: [main]` + `on.pull_request.branches: [main]`. Do not broaden `push` to all branches.
**Warning signs:** Two CI runs per PR commit.

## Code Examples

### Coverage exclusion pragma around the CLI bootstrap guard (the D-03 mechanism)
```javascript
// Source: nodejs.org/docs/latest-v24.x/api/test.html (Coverage), Node 24
// The CLI bootstrap (source ~721-739) never runs under the test process (the test imports the
// module; import.meta.url !== process.argv[1]). Wrap it so the 100% global gate stays honest.
/* node:coverage disable */
if (process.argv[1] && fileURLToPath(import.meta.url) === path.resolve(process.argv[1])) {
  // ... CLI bootstrap (argv parse, writeFileSync, process.exit) ...
}
/* node:coverage enable */
```
Pragma facts (VERIFIED): only `node:coverage` comments are honored by the built-in runner (NOT `c8`/`v8` comments); `disable`/`enable` brackets a block; `ignore next [N]` skips a single line (or N) but the no-count `ignore next` form is "inconsistent/unpredictable" per community guidance -- prefer the `disable`/`enable` block for the multi-line bootstrap. `[VERIFIED: nodejs.org test runner docs; electrovir.com 2024-08-17]`
