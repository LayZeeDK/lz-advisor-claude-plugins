scripts so `node --test` runs -- and test coverage is enforced -- on every push/PR. It is pure
build/test infrastructure; it adds NO product capability and does not touch the aggregator source,
the schema, or any skill/agent.

**In scope (FIXED by ROADMAP Phase 17.3):**

  Claude agent skill scripts.
- A GitHub Actions "CI" workflow with a `test` job that runs `node --test` across all bundled
  lz-advisor plugin scripts (today: the one aggregator test file; the discovery form must auto-pick
  up future `*.test.mjs` files).
- The CI workflow calculates and ENFORCES test coverage in all supported dimensions -- and, if
  feasible, MC/DC plus coverage of nullish-coalescing (`??`) and optional-chaining (`?.`)

- A `concurrency` strategy (group by ref/workflow with in-progress cancellation) so superseded
  runs on the same branch/PR are cancelled.

  needs).

### Coverage tooling

- **D-01:** Use Node's BUILT-IN test-runner coverage (`node --test --experimental-test-coverage`),
  with ZERO external coverage dependencies. The aggregator under test is deliberately
  Node-stdlib-only (`node:fs`, `node:path`, `node:url`); adding c8/istanbul/nyc/vitest would break
  that zero-dependency ethos for marginal value. The repo has no root `package.json` and should not
  grow a dependency tree just to run coverage. (Alternative considered, not chosen: c8/istanbul --
  richer reports and MC/DC-ish output, but pulls a dependency tree into a zero-dep repo. Rejected;
  recorded so the planner does not re-litigate.)

### Coverage dimensions and thresholds

- **D-02:** Enforce LINE, BRANCH, and FUNCTION coverage using the built-in threshold flags
  (`--test-coverage-lines`, `--test-coverage-branches`, `--test-coverage-functions`), which fail
  the job in-process when coverage drops below the configured percentage (fail-closed gate). These
  three are the dimensions Node's built-in coverage "supports", satisfying "all supported
  dimensions".
- **D-03:** Target 100% on the LIBRARY surface. The 42-test / 951-LOC suite over the 739-LOC source
  is comprehensive, so a high gate is realistic. The likely-uncovered region is the CLI bootstrap
  guard (`if (import.meta.url === ...) main()`) which does not run under the test process. Disposition:
  prefer `// node:coverage disable`/`ignore` pragmas around genuinely-unreachable bootstrap lines so
  the GLOBAL gate stays meaningful at 100%, rather than lowering the global threshold to absorb dead
  bootstrap lines. The EXACT enforced numbers are set during planning after a one-time measurement
  run on the pinned Node version (the planner/researcher reports the achieved figure and the chosen
  gate). Lowering a dimension's gate below 100% requires an explicit, justified note.

### MC/DC and `??` / `?.` operator coverage (the roadmap's "if feasible")

- **D-04:** MC/DC and operator-level nullish/optional-chaining coverage are NOT feasible with
  zero-dependency tooling and are documented as attempted-and-infeasible, NOT pursued. Grounds:
  (1) Node's built-in coverage reports line/branch/function only -- no condition-level MC/DC, no
  per-operator `??`/`?.` coverage; (2) MC/DC (a DO-178C condition-coverage metric) has no mainstream
  zero-dep JS tooling; (3) the source contains ZERO `?.` sites and exactly ONE `??` site, so
  operator coverage is near-moot -- the single `??` branch is exercised under ordinary BRANCH
  coverage (D-02). Adding a coverage dependency purely to chase MC/DC would violate the zero-dep
  constraint (D-01) for negligible signal. (HIGH confidence: this is a factual capability limit, not
  a preference. Reversible if a zero-dep MC/DC tool ever emerges.)

### Test discovery form

- **D-05:** Discover tests via Node's built-in runner GLOB scoped to the bundled plugin scripts --
  e.g. `node --test "plugins/lz-advisor/skills/**/*.test.mjs"` (exact spec/quoting finalized in
  planning) -- so newly-added `*.test.mjs` files are picked up automatically without editing the
  workflow. Do NOT pass a bare DIRECTORY argument: the `node --test <dir>` spurious-exit-1 quirk is
  HOST-specific to this Windows arm64 dev machine; CI runs on `ubuntu-latest` where glob/default
  discovery works, but the explicit glob is the robust, intention-revealing form. (The local
  FILE-form gate convention from Phase 16 D-13 remains the DEV-host convention; CI uses the glob.)

### Node version pin

- **D-06:** Format is LOCKED by the roadmap: a `.node-version` file containing `lts/<codename>`.
  Recommended value is the current Active LTS codename; the EXACT codename is research-confirmed
  against the authoritative Node.js release schedule (and any Claude Code skill-runtime guidance)
  before writing -- candidate as of the knowledge cutoff is `lts/krypton` (Node 24, entered Active
  LTS 2025-10), with `lts/jod` (Node 22) as the conservative fallback. `actions/setup-node` consumes
  the file via `node-version-file: .node-version` (it accepts the `lts/<codename>` alias). This is a
  SINGLE pinned version, NOT a matrix -- the scripts target the single Claude-agent runtime and a
  matrix adds cost/noise without value for stdlib-only scripts. fnm (the dev machine's manager) also
  reads `lts/<codename>` from `.node-version`, so local and CI resolve the same line.

### Triggers, concurrency, and permissions

- **D-07:** Triggers: `pull_request` (PRs targeting the default branch) PLUS `push` to the default
  branch (`main`). This covers "every push/PR" while avoiding the double-run that fires when both
  the push-to-PR-branch and the pull_request events trigger -- PRs are validated via `pull_request`,
  post-merge signal via `push: main`.
- **D-08:** Concurrency (roadmap-locked): `group: ${{ github.workflow }}-${{ github.ref }}` with
  `cancel-in-progress: true`, so a superseded run on the same branch/PR is cancelled.
- **D-09:** Permissions (roadmap-locked): top-level `permissions: { contents: read }`
  (default-minimal). The `test` job needs nothing beyond reading the repo to check out and run
  tests -- no `checks: write`, no `pull-requests: write`. Any future coverage-comment/badge feature
  would get its own narrowly-scoped grant in its own phase.
- **D-10:** Workflow file at `.github/workflows/ci.yml`, `name: CI`, job id `test`. Standard
  convention; the roadmap names the workflow "CI".

### Claude's Discretion

- Exact YAML structure and step ordering; whether `actions/checkout` and `actions/setup-node` are
  pinned by major tag vs full commit SHA (research may recommend SHA-pinning third-party actions as
  supply-chain hygiene -- defer to the researcher's authoritative recommendation).
- Whether coverage thresholds are expressed as CLI flags or a coverage config block, and the exact
  achieved/enforced percentage (set after the measurement run, per D-03).
- Whether the `??`-site branch needs an added assertion to satisfy 100% branch coverage, or is
  already exercised by the existing 42 tests.
- Plan-file breakdown and wave structure (this is small and cohesive -- likely a single plan:
  `.node-version` + `ci.yml`).

## Existing Code Insights

### Reusable Assets

- Exactly TWO bundled scripts today, both under
  `plugins/lz-advisor/skills/lz-deep-research/scripts/`: the aggregator source and its `.test.mjs`.
  The CI discovery glob (D-05) is designed so additional `skills/**/*.test.mjs` files are auto-run
  without workflow edits.
- The test suite already uses the built-in `node:test` runner + `node:assert` -- the same runner CI
  invokes. No test-framework migration needed; CI just adds `--experimental-test-coverage` + the
  threshold flags.

### Established Patterns

- **Zero external dependencies** is a load-bearing project ethos (the aggregator is stdlib-only;
  there is no root `package.json`). D-01/D-04 keep CI within it -- built-in coverage only, no
  c8/istanbul, no MC/DC dependency.
- **Fail-closed gates:** the project favors fail-closed contract enforcement in code; D-02 mirrors
  that for CI -- coverage below threshold FAILS the job rather than warning.
- **`node --test` FILE-form on the dev host:** the Windows arm64 dev machine spuriously exits 1 on
  the bare-directory form; CI (ubuntu) uses the glob form (D-05). This is a known host quirk, not a
  CI concern.

### Integration Points

- No existing `.github/` directory -- this phase CREATES `.github/workflows/ci.yml` (and the root
  `.node-version`) from scratch. Nothing else in the repo references CI yet.
- The pinned Node version (D-06) must be recent enough that the built-in coverage threshold flags
  (`--test-coverage-lines` etc.) are available -- they landed in Node 22+. The researcher confirms
  flag availability for the chosen codename alongside the `setup-node` `node-version-file`
  `lts/<codename>` alias support.
