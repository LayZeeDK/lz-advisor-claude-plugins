## Warnings

### WR-01: TEST-2 does not test the `listJson` `.sort()` it claims to guard (tautology persists)

**File:** `plugins/lz-advisor/skills/lz-deep-research/scripts/lz-deep-research-aggregate.test.mjs:400-461`

**Issue:** TEST-2 ("cross-file-order stability") was added specifically to close
the prior-review TEST-2 tautology, and its comment asserts: *"This is stable
ONLY because listJson sorts the directory listing before processing; if
listJson's .sort() were removed, readdirSync's raw OS order could surface
z-worker first ... would let the output drift."* That claim is false, and the
test does not discriminate the sort. Two independent proofs from this review:

1. **Mutation:** Deleting `.sort()` from `listJson` leaves the full suite at
   25/0 green (mutation SURVIVED). The test it is supposed to defend does not
   fail.
2. **Root cause (host-independent):** `survivors[0]` ordering is determined by
   `rankClusters` (corroboration DESC, then `normalize(text)` lexical ASC), which
   is fully independent of file read order. Forcing `listJson` to return the
   WORST case (`.sort().reverse()`, i.e. `z-worker` before `a-worker`) still
   yields `survivors[0].claim === 'alpha beats beta always'` because the rank
   step re-sorts. The `.sort()` in `listJson` is masked by the downstream
   lexical tiebreak and is not observable through `survivors[0]`.
3. **Host aggravator:** On this host `readdirSync` already returns entries in
   alphabetical order regardless of creation order (verified: writing
   `z-worker.json` then `a-worker.json` returns `["a-worker.json",
   "z-worker.json"]`), so even the read order the test tries to perturb is not
   actually perturbed locally.

The `deepEqual` second-run cross-check (lines 456-457) only proves run-to-run
determinism, not read-order independence, so it does not rescue the assertion.

**Fix:** Either (a) drop the false "ONLY because listJson sorts" claim and
re-scope TEST-2 honestly to "determinism of `survivors[0]` under the rank
tiebreak" (it does test that), or (b) make the test actually exercise read order
by targeting a property the rank step does NOT normalize away. A genuine sort
guard must observe `listJson` output directly, e.g.:
```js
import { mergeClusters } from './lz-deep-research-aggregate.mjs';
// Two NON-mergeable same-corroboration claims whose ORIGINAL cluster ids depend
// on first-seen (read) order: cluster0 goes to whichever file is read first.
// With .sort(), a-worker is read first -> its claim is cluster0. Assert the
// cluster id (PRE-rank, read-order-sensitive), not survivors[0] (POST-rank).
const { clusters } = mergeClusters(runDir);
const aCluster = clusters.find((c) => c.text === aClaim);
assert.equal(aCluster.id, 'cluster0',
  'alphabetically-first worker must be assigned cluster0 (read order = sorted)');
```
Cluster ids are assigned by first-seen order in `mergeClusters` and are NOT
re-sorted downstream, so this assertion genuinely fails if `.sort()` is removed
on a host where `readdirSync` is unsorted. (Note: this still will not fail on a
host that pre-sorts `readdirSync`; a fully host-independent test would inject a
stub directory listing. At minimum, correct the misleading comment.)

### WR-02: Path-traversal `ContractError` from `quoteOutcome` carries no `.file` (inconsistent with the AGG-5/6/7 annotation work)

**File:** `plugins/lz-advisor/skills/lz-deep-research/scripts/lz-deep-research-aggregate.mjs:357` (and `383-419` caller)

**Issue:** The entire AGG-3/5/6/7 batch exists to make every `ContractError`
carry `.file` so the CLI's `(${err.file})` annotation (line 653) names the
offending file. `loadExcerpts` was updated to pass the path to `safeId` (AGG-6,
verified working: a malformed excerpt filename throws with
`.file = <excerptPath>`). But the security-most-relevant abort -- a worker that
authored a path-traversal `excerpt_id` such as `'../evil'` -- goes through
`quoteOutcome`, which calls `safeId(String(member.excerpt_id))` **without** the
file argument. Verified at runtime: that `ContractError.file` is `undefined`, so
the CLI prints `lz-deep-research-aggregate: unsafe id (path traversal rejected):
"../evil"` with **no file annotation**. The operator cannot tell which
`claims/<worker>.json` authored the malicious id -- exactly the case where
provenance matters most. (TEST-9 only asserts the throw, not the annotation, so
it does not surface this.) The id string is in the message, which partially
mitigates, but the file is omitted only on this one path.

**Fix:** Thread the source file path into `quoteOutcome` so the abort annotates
the worker file. `recheckClusters` iterates members but does not currently carry
the originating claims-file path; the cleanest minimal change is to stamp each
raw claim with its source file in `mergeClusters` (it already does
`raw.push({ ...c, source: w.source })` at line 257) and pass it through:
```js
// mergeClusters, line 257:
raw.push({ ...c, source: w.source, _file: path.join(claimsDir, f) });
// quoteOutcome, line 357:
const citedId = member.excerpt_id == null
  ? null
  : safeId(String(member.excerpt_id), member._file);
```
This matches the AGG-5/6/7 intent (every contract abort names its file) and
removes the lone unannotated path. If deemed out of scope for 17.1, record it
explicitly as a deferred item rather than leaving the annotation gap silent.

### WR-03: `WR-04` identifier is overloaded across the three artifacts (traceability collision)

**File:** `plugins/lz-advisor/references/lz-deep-research-schema.md:147` and `:251`; `plugins/lz-advisor/skills/lz-deep-research/scripts/lz-deep-research-aggregate.mjs:235,360`; `...test.mjs:293`

**Issue:** The finding label `WR-04` now denotes two unrelated things:
- In the **test** (`test('WR-04 claim missing id ...')`, line 293) and the
  **schema** claim-record row (line 147), `WR-04` = the missing-`id` fail-closed
  guard.
- In the **aggregator source** (line 360, `// WR-04 (accepted, frozen): the
  re-check is a normalized-SUBSTRING test ...`) and the **schema** section
  heading (line 251, `### WR-04 caveat (normalized-substring ...)`), `WR-04` =
  the lower-bound substring-match caveat -- a completely different concern.

Meanwhile the source comment for the missing-id guard (line 235) labels it
`AGG-1`, so the same fix is `AGG-1` in the code but `WR-04` in the test and
schema. The schema author noticed the clash and added a parenthetical disclaimer
(line 147: *"the source labels this guard WR-04, which also names the unrelated
normalized-substring caveat section below"*) rather than resolving it. A future
maintainer grepping `WR-04` to trace the missing-id guard will land on the
substring caveat in the source, and vice versa. This is a documentation/
traceability defect, not a behavioral one.

**Fix:** Pick one label per concern and apply it consistently across all three
files. Recommended: keep `AGG-1` for the missing-id guard everywhere (source
already uses it; rename the test to `AGG-1/WR-04 claim missing id ...` or just
`AGG-1`, and update the schema row to cite `AGG-1`), and keep `WR-04` solely for
the normalized-substring caveat. Then drop the schema's self-referential
disclaimer parenthetical, which exists only to paper over the collision.

### IN-01: AGG-1 comment cites a fixture whose vote files are never read as evidence the member-id fallback is "in active use"

**File:** `plugins/lz-advisor/skills/lz-deep-research/scripts/lz-deep-research-aggregate.mjs:238-240`

**Issue:** The AGG-1 guard comment justifies the fix by stating the member-id
vote-file fallback is "in active use: the wrong-passage-downgraded **and
fabricated-quote-dropped** committed fixtures name their vote files by member id
(e.g. c1-0.json)." The `fabricated-quote-dropped` fixture's claim is `dropped` at
the quote re-check (its quote `"X cures Z completely"` is absent from its cited
`e1.txt` and there is no other excerpt), which is UPSTREAM of `tally`. Its
`c1-0/1/2.json` vote files are therefore never read -- dead fixtures. Only
`wrong-passage-downgraded` (claim survives as `downgraded`, reaches `tally`,
vote files `c1-*.json` consulted via the member-id fallback) genuinely
exercises the fallback. The substantive claim (the fallback is live) is true,
but the cited evidence is half-wrong and could mislead a maintainer into
believing the fabricated fixture covers the fallback path.

**Fix:** Trim the parenthetical to the fixture that actually exercises the
fallback through to `tally`: *"... the wrong-passage-downgraded committed fixture
names its vote files by member id (c1-0.json) and reaches tally via the
member-id fallback."* Drop the `fabricated-quote-dropped` reference (or note its
vote files are dead because the claim drops upstream of tally).

## Resolution (post-review fixes, same phase)

The review ran as the phase's advisory code-review gate. Because WR-01 was an
empirically-proven violation of ROADMAP SC-3 and Plan 17.1-02's must_have (not a
style nit), the load-bearing findings were fixed in-phase rather than deferred to a
gap-closure cycle:

- **WR-01 (fixed):** `listJson` gained an injectable `readdir` seam (default
  `fs.readdirSync`, production callers byte-for-byte unaffected) and is now exported.
  TEST-2 was rewritten to drive that seam with a deliberately unsorted listing and
  assert lexical output -- a host-independent guard. A mutation harness confirmed
  removing `listJson`'s `.sort()` now flips TEST-2 from pass to fail (it previously
  survived 25/0). TEST-2b was split out to own the run-to-run determinism check.
  Suite: 26/26 green. Satisfies SC-3 literally ("removing `.sort()` would cause a
  test failure").
- **WR-02 (fixed):** each raw claim is stamped with its originating `_file` in
  `mergeClusters`; `quoteOutcome` passes it to `safeId`, so a rejected
  path-traversal `excerpt_id` now aborts with `.file` set and the CLI names the
  offending worker file. Closes the lone unannotated `ContractError` the AGG-5/6/7
  batch missed. `_file` is internal (the survivor record is built explicitly and
  never spreads the member, so it does not leak into `survivors.json`).
- **IN-01 (fixed):** the AGG-1 comment now cites only `wrong-passage-downgraded`
  (which reaches `tally` via the member-id fallback); the `fabricated-quote-dropped`
  reference -- whose vote files are never read because the claim drops upstream of
  `tally` -- was removed.
- **WR-03 (deferred, with rationale):** the recommended resolution (rename the
  missing-id test away from `WR-04`) conflicts with ROADMAP SC-4's literal "WR-04
  test exists" wording and Plan 17.1-02's `git grep -n "WR-04"` must_have. The clash
  is documentation/traceability only (no behavioral impact) and the schema already
  carries a disambiguating disclaimer. Resolving it cleanly requires a coordinated
  source+schema+test relabel that also re-touches a frozen Phase-16/17 caveat
  comment -- out of scope for this gap-closure phase, recorded here for a future
  renumbering pass.
