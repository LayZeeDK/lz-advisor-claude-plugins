### Pattern 1: R1-1 read-time path-safety (PRIMARY -- exact analog of 17.1 WR-02)

**What:** Reject a path-traversal claim `id` at the read boundary in `mergeClusters`, annotated with
the originating worker file, BEFORE it propagates downstream.
**Where:** Immediately AFTER the existing AGG-1 non-empty guard at `:250-251`, BEFORE the text guard.
**Why here:** `_file` is `path.join(claimsDir, f)` -- the exact value already stamped at `:271` and
already in scope inside the `for (const c of w.claims)` loop. The read boundary is where provenance
is unambiguous.

```javascript
// Source: lz-deep-research-aggregate.mjs mergeClusters, after the AGG-1 guard (:250-251)
if (typeof c.id !== 'string' || c.id.length === 0) {
  throw new ContractError('claim missing non-empty id', path.join(claimsDir, f));
}
// R1-1 (NEW): a path-traversal claim id (e.g. "../evil") must be rejected at READ time with the
// originating worker file, not LATE in tally() with a .file-less ContractError. safeId already
// throws ContractError('unsafe id (path traversal rejected): ...', file); we discard the return
// value here (c.id is unchanged) -- the call is purely a validating side-effect at the boundary.
safeId(c.id, path.join(claimsDir, f));
```

Note: `safeId` returns the id unchanged on success and throws on failure. At the read boundary the
return value is discarded (the existing AGG-1 check already proved non-empty-string; `safeId`'s own
type/empty check is harmlessly redundant here, then the path-traversal check is the load-bearing
addition). The planner MAY collapse the AGG-1 non-empty guard into the `safeId` call since `safeId`
itself throws `'invalid id (expected non-empty string)'` on a non-string/empty id -- but that changes
the WR-04 message text `'claim missing non-empty id'` that the existing WR-04 test (`:305`) asserts on
(`/missing non-empty id/`). **Do NOT collapse the AGG-1 guard** -- keep both (the non-empty guard for
the existing WR-04 message, then `safeId` for the path-traversal addition), or the WR-04 regression
breaks. (See Pitfall 1.)

### Pattern 2: R1-1 defense-in-depth `.file` annotation in `tally` (belt-and-suspenders)

**What:** Thread a `file` argument into `tally`'s two `safeId` calls so no `safeId` call anywhere can
throw a `.file`-less `ContractError`.
**Where:** `tally` `:501-502`.

```javascript
// Source: lz-deep-research-aggregate.mjs tally (:500-502) -- current state:
//   const votesDir = path.join(runDir, 'votes');
//   const clusterId = safeId(cl.id);
//   const memberId = cl.members && cl.members[0] ? safeId(String(cl.members[0].id)) : null;
//
// R1-1 defense-in-depth -- annotate with the best-available file. The cluster id is derived from
// 'cluster' + N (never worker-authored, so a traversal is structurally impossible) and the member
// id is now pre-validated at read-time by Pattern 1; these annotations exist so the discipline is
// uniform, not because either is now a live attack path. Use the first member's _file when present:
const votesDir = path.join(runDir, 'votes');
const memberFile = cl.members && cl.members[0] ? cl.members[0]._file : undefined;
const clusterId = safeId(cl.id, memberFile);
const memberId = cl.members && cl.members[0] ? safeId(String(cl.members[0].id), memberFile) : null;
```

**Discretion:** D-01 says the tally annotations are belt-and-suspenders and the `file` arg "either is
correct" to add in the same edit or a follow-on hunk. The `_file` is available on cluster members
(stamped at `:271`, carried through merge/recheck via `{ ...m }` spreads). The planner may instead
pass `path.join(runDir, 'votes')` or omit the arg if it judges the member `_file` plumbing not worth
the churn -- but threading `cl.members[0]._file` is the faithful realization of "name the offending
worker file." Confirm `_file` survives `recheckClusters` (it does: `:419` does `{ ...m, quote_outcome }`
which preserves `_file`, and `:429` does `{ ...cl, members: survivingMembers, ... }`).

### Pattern 3: R2-1 non-object vote-record guard (exact code from D-02)

**What:** Guard the parsed vote record before the `.verdict` read so a literal-`null` (or non-object
primitive) vote file fails closed with a `ContractError` carrying the file, not a raw `TypeError`.
**Where:** `tally` `:522`, replacing `const verdict = readJson(f).verdict;`.

```javascript
// Source: lz-deep-research-aggregate.mjs tally (:522) -- current state:
//   const verdict = readJson(f).verdict;
//   seats.push(verdict == null ? 'insufficient' : verdict);
//
// R2-1 fix (D-02): a literal-null / non-object vote file is malformed worker output (a structural
// violation -- there is no record), categorically distinct from a well-formed record whose `verdict`
// field is merely absent/null (which legitimately stays lenient -> 'insufficient' below). Fail closed.
const rec = readJson(f);
if (rec == null || typeof rec !== 'object') {
  throw new ContractError('malformed vote record (expected object): ' + JSON.stringify(rec), f);
}
const verdict = rec.verdict;
seats.push(verdict == null ? 'insufficient' : verdict); // PRESERVED unchanged (:523)
```

**Critical:** The `:523` line `verdict == null ? 'insufficient' : verdict` is PRESERVED byte-for-byte.
The R2-1 guard fires only on a structurally-null/non-object RECORD; a present `{ }` object with no
`verdict` key, or `{ "verdict": null }`, still flows to the lenient `insufficient` path. (Also note
`typeof rec !== 'object'` catches numbers/strings/booleans; `typeof null === 'object'` is why the
explicit `rec == null` term is needed first. Arrays pass `typeof === 'object'` and would read
`.verdict` as `undefined` -> `insufficient`; D-02's wording is "non-object (null or primitive)", so
an array is NOT rejected by this guard -- which is consistent with the lenient-on-missing-field
posture. The planner should not add an `Array.isArray` rejection unless a recovered finding demands
it; that would be scope creep beyond D-02.)

### Anti-Patterns to Avoid

- **Collapsing the AGG-1 non-empty guard into the `safeId` call (R1-1):** `safeId` throws
  `'invalid id (expected non-empty string)'`, not `'claim missing non-empty id'`. The existing WR-04
  test asserts `/missing non-empty id/`. Removing the non-empty guard breaks that test. Keep BOTH.
- **Rejecting an array vote record under R2-1:** D-02 scopes the guard to "non-object (null or
  primitive)". An array passes `typeof === 'object'`; reading `.verdict` yields `undefined` ->
  `insufficient` (the lenient path). Adding `Array.isArray` rejection is scope creep beyond D-02.
- **Touching `:523` leniency:** the present-but-null-`verdict` -> `insufficient` behavior is
  intentional and frozen. R2-1 guards the RECORD, not the FIELD.
- **Deleting the `WR-04` token:** breaks ROADMAP SC-4's literal "WR-04 test exists" and the 17.1-02
  `git grep WR-04` must_have. Alias, don't delete.
- **Asserting only the throw, not the annotation:** the WR-02 / TEST-9 lesson is that
  `assert.throws(..., /pattern/)` does NOT verify `err.file`. The D-04 tests must assert `err.file`
  and the error constructor (see Validation Architecture).
- **Using the dir-form node:test gate:** `node --test <dir>` spuriously exits 1 on this host. Gate is
  FILE-form only.

## Common Pitfalls

### Pitfall 1: R1-1 -- breaking the existing WR-04 message contract

**What goes wrong:** Replacing the AGG-1 `'claim missing non-empty id'` guard with `safeId` alone
(reasoning "safeId already type-checks"). The existing WR-04 test at `:293-309` asserts
`assert.throws(() => aggregate(runDir), /missing non-empty id/)`. `safeId`'s empty-id message is
`'invalid id (expected non-empty string)'` -- a DIFFERENT string -- so the assertion fails.
**Why it happens:** The two checks look redundant (both reject empty ids).
**How to avoid:** KEEP the AGG-1 non-empty guard for its existing message, then ADD the `safeId` call
immediately after it for the path-traversal axis. Both lines coexist.
**Warning signs:** The WR-04 test (`:293`) flips from pass to fail after the R1-1 edit.

### Pitfall 2: R2-1 -- disturbing the present-but-null-`verdict` leniency

**What goes wrong:** Folding the new RECORD guard and the existing FIELD leniency into one check, or
moving the guard below the `.verdict` read.
**Why it happens:** Both deal with "null" and look mergeable.
**How to avoid:** Two distinct concepts: (a) `rec` is structurally null/non-object -> FAIL CLOSED
(R2-1, new); (b) `rec.verdict` is absent/null on a valid object -> LENIENT `insufficient` (`:523`,
preserved). The guard sits BETWEEN `readJson(f)` and `rec.verdict`. The PIPE-07-tier fixtures
(`unsupported-no-votes`, etc.) and the `:523` leniency must still behave identically after the fix --
re-run the full suite to confirm.
**Warning signs:** Any PIPE-07 confidence-tier test changes its result; the `Unsupported` tier test
flips.

### Pitfall 3: Mutation-verification omitted (the TEST-2 tautology class)

**What goes wrong:** A regression test passes on the fixed code but would ALSO pass if the guard were
removed -- a tautology (the exact defect 17.1's WR-01 caught in TEST-2, and the methodology the 17.1
mutation harness institutionalized).
**Why it happens:** Asserting `assert.throws(() => aggregate(runDir))` without pinning WHICH error /
which `.file` -- a different pre-existing guard might be doing the throwing.
**How to avoid:** For R1-1, the path-traversal id must reach `safeId` -- ensure the claim has valid
`text`/`quote`/`source` so it passes the earlier guards, and assert on `/path traversal rejected/`
AND `err.file` ending in the worker filename. Then MUTATION-VERIFY: temporarily remove the new
`safeId(c.id, ...)` call and confirm the test FAILS (the id would otherwise be rejected only LATE in
`tally` -- where `safeId(cl.id)` is `.file`-less -- so the `err.file` assertion is what discriminates
read-time from late rejection). For R2-1, mutation-verify by reverting to
`const verdict = readJson(f).verdict` and confirming the test now throws a `TypeError` (not the
`ContractError` the assertion demands) -> test FAILS.
**Warning signs:** The new test stays green when its guard line is deleted.

### Pitfall 4: R1-1 regression test -- distinguishing read-time from late rejection

**What goes wrong:** A path-traversal-id test that asserts only `/path traversal rejected/` passes
even WITHOUT the R1-1 fix, because `tally`'s late `safeId(cl.id)` (`:501`) ALSO rejects it (just with
`.file === undefined`). So the throw alone does not discriminate the fix.
**Why it happens:** The late guard already throws the same message.
**How to avoid:** The discriminating assertion is `err.file` -- it is `undefined` under the old
behavior (late rejection in `tally`) and equals the worker file path under R1-1 (read-time rejection
in `mergeClusters`). Assert `typeof err.file === 'string'` and `err.file.endsWith('w1.json')` (or the
`path.basename`). This is the assertion that FAILS when the R1-1 fix is removed -- it is the genuine
mutation-killing assertion. **Caveat:** because the late `tally` guard also annotates `.file` once the
Pattern-2 defense-in-depth `file` args are added, the test must run BEFORE/INDEPENDENT of that change
to be a clean read-time discriminator -- OR assert that the error surfaces from the `mergeClusters`
phase. Simplest robust approach: a path-traversal id with an OTHERWISE-VALID claim that would survive
to a survivor record; under the old code it reaches `tally` and (with defense-in-depth) annotates with
the member `_file` anyway -- so to keep the test a clean read-time discriminator, assert the throw
happens (it always does) AND `err.file` names the worker. The cleanest mutation kill is: remove the
read-time `safeId` AND keep `tally`'s as `.file`-less (original) -> `err.file` is `undefined` -> test
fails. Document this two-line mutation in the test comment.

> Planner note: if Pattern-2 (tally defense-in-depth `.file`) lands in the SAME commit as Pattern-1
> (read-time guard), the `err.file`-presence assertion alone no longer uniquely discriminates the
> read-time guard (tally would now also set `.file`). To keep the R1-1 test a faithful read-time
> regression lock, EITHER (a) assert the error originates at the merge stage (e.g. by constructing a
> claim that is dropped at quote-recheck so it never reaches `tally` -- then only the read-time guard
> can reject it), OR (b) accept that the test guards the combined "`safeId` on `c.id` carries `.file`"
> property and document the mutation as "remove read-time guard AND revert tally to `.file`-less".
> Option (a) is the stronger, more surgical regression lock -- recommended.

### Pitfall 5: Frozen-contract drift

**What goes wrong:** A fix accidentally touches the tally rubric branch order, the confidence enum,
the survivor-record field set, or the quote-recheck semantics -- all frozen by Phase 16/17 and
consumed by Phase 18/20.
**Why it happens:** The fixes live inside `tally` and `mergeClusters`, adjacent to frozen logic.
**How to avoid:** R1-1 adds a guard at the read boundary (before any rubric logic); R2-1 adds a guard
before the `.verdict` read (before the `refuted`/`unrefuted` counting and the branch decision). NEITHER
touches the branch order (`:550-566`), the enum, the survivor record (`:594-601`), or `quoteOutcome`.
The full existing suite (26 tests, including all PIPE-07 tiers, the survivor-record shape, and the
5-label stdout line) MUST stay green -- that suite IS the frozen-contract regression guard.
**Warning signs:** Any existing PIPE-07 / SC5-* / CR-01 test changes outcome.

### R2-1 regression test (mutation-verified, asserts ContractError not TypeError)

```javascript
// A literal-null vote file (well-formed JSON `null`) must raise a ContractError carrying the file,
// NOT a raw TypeError from null.verdict. Build a surviving single claim (matching excerpt so it
// passes quote-recheck and reaches tally), then write votes/cluster0-0.json containing literal null.
test('R2-1 literal-null vote record fails closed with ContractError naming the file (not TypeError)', () => {
  const runDir = fs.mkdtempSync(path.join(os.tmpdir(), 'lz-dr-nullvote-'));
  const claimsDir = path.join(runDir, 'claims');
  const excerptsDir = path.join(runDir, 'excerpts');
  const votesDir = path.join(runDir, 'votes');
  fs.mkdirSync(claimsDir, { recursive: true });
  fs.mkdirSync(excerptsDir, { recursive: true });
  fs.mkdirSync(votesDir, { recursive: true });

  try {
    fs.writeFileSync(
      path.join(claimsDir, 'w1.json'),
      JSON.stringify({
        worker: 'w1',
        source: 's1',
        claims: [{ id: 'c1', text: 'X reduces Y by 30%', quote: 'X reduces Y by 30%', excerpt_id: 'e1' }],
      }),
      'utf8',
    );
    fs.writeFileSync(path.join(excerptsDir, 'e1.txt'), 'The study found that X reduces Y by 30% overall.', 'utf8');
    // The seat the claim reads (cluster0-0): the JSON literal null -- parses cleanly, returns null.
    fs.writeFileSync(path.join(votesDir, 'cluster0-0.json'), 'null', 'utf8');

    let caught;
    assert.throws(
      () => aggregate(runDir),
      (err) => {
        caught = err;
        return err.name === 'ContractError'; // NOT a raw TypeError
      },
    );
    assert.equal(caught.name, 'ContractError', 'a null vote record must fail closed as ContractError');
    assert.ok(/malformed vote record/.test(caught.message), 'message names the malformed-record cause');
    assert.equal(typeof caught.file, 'string');
    assert.ok(caught.file.endsWith('cluster0-0.json'), 'ContractError.file must name the offending vote file');
  } finally {
    fs.rmSync(runDir, { recursive: true, force: true });
  }
});
```

**Mutation to kill:** revert `tally`'s guard to `const verdict = readJson(f).verdict;`. Expected
result without the fix: `null.verdict` throws a `TypeError` whose `name` is `'TypeError'` (not
`'ContractError'`) and whose `.file` is `undefined` -> the `err.name === 'ContractError'` predicate is
false -> `assert.throws` rejects the error -> test FAILS. This is a genuine, non-tautological kill.

**Note on the seat lookup:** the surviving claim is `cluster0` (first cluster, `'cluster' + 0`); its
vote seat 0 is looked up as `votes/cluster0-0.json` FIRST (`:507`), so writing the null record there
guarantees `tally` reads it (cluster-id lookup hits before the member-id fallback).
