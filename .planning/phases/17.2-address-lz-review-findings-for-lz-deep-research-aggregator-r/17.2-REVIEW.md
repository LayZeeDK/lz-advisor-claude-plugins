## Summary

Adversarial review of the three Phase-17.2 changes (diff base `7c5a8da..HEAD`): the R1-1
read-time `safeId(c.id, ...)` claim-id guard plus `.file`-threaded `tally` safeId calls; the
R2-1 non-object vote-record `ContractError` guard; the two mutation-verified regression tests;
and the WR-04 -> AGG-1 / QR-01 documentation relabel.

The changes are correct. I verified them three ways beyond reading:

1. **Full suite passes (28/28)** via the host FILE-form gate
   (`node --test ...lz-deep-research-aggregate.test.mjs`).
2. **Both new tests are genuine mutation killers.** Reverting the R2-1 guard to the bare
   `readJson(f).verdict` fails exactly the R2-1 test (and nothing else); removing the read-time
   `safeId(c.id, ...)` line from `mergeClusters` fails exactly the R1-1 test. Neither is a
   tautology -- each fails iff its target line is removed.
3. **R2-1 leniency boundary holds as documented.** Direct probing confirms: an array vote record
   stays lenient (`typeof 'object'`, `.verdict` undefined -> `insufficient` -> Low); a
   present-but-null `verdict` FIELD stays lenient (the preserved leniency -> Low); a non-object
   (number) vote record fails closed with `ContractError('malformed vote record ...')`. This
   matches the inline contract exactly (the `rec == null` term first because `typeof null ===
   'object'`; no `Array.isArray` rejection, avoiding scope creep beyond D-02).

**Frozen contracts are intact.** The diff contains zero changes to `CEILINGS`, the tally rubric
branch order, the confidence enum, or the survivor-record shape -- confirmed by grepping the diff
for those tokens (no matches). The R1-1 `tally` change only threads an OPTIONAL `file` arg into
two pre-existing `safeId` calls (return values discarded; `cl.id`/`memberId` unchanged), so it is
behavior-preserving for production callers. `_file` provenance survives `recheckClusters`
(`{ ...m }` at member spread, `{ ...cl, members: survivingMembers }` at cluster spread) and never
leaks into `survivors.json` (the survivor record is built explicitly, never by spreading a
member). The relabel is consistent: `WR-04` no longer appears in the `.mjs`; the substring caveat
is uniformly `QR-01` in both code comment and schema heading; the schema's `claims[].id` row now
reads `AGG-1` with the `WR-04` test co-label explicitly annotated.

No Critical or Warning findings. Two Info-level comment-accuracy nits remain (stale line-number
annotations introduced by the line shift from the inserted blocks). They are documentation
precision only -- no behavioral, security, or maintainability impact.

### IN-01: Stale line-number annotations in `tally` and the R1-1 test comment

**File:** `plugins/lz-advisor/skills/lz-deep-research/scripts/lz-deep-research-aggregate.mjs:513,539`
**Issue:** The inserted R2-1/R1-1 blocks shifted line numbers, but several inline comments still
cite the pre-insert positions:
- Line 539 says the verdict-null leniency lands "on the next line (the :523 leniency,
  PRESERVED)" -- the actual leniency line is now 550.
- Line 513 (the `tally` `_file`-survival note) cites "`recheckClusters` (:419 `{ ...m }`, :429
  `{ ...cl, members: survivingMembers }`)" -- the actual spread lines are now 427 and 435.
- In the test, the R2-1 comment says the cluster-id lookup hits "first (:507 region)" -- the
  lookup is now around line 520.

The textual claims (which line does what) are all CORRECT; only the numeric `:NNN` anchors
drifted. None of this affects behavior.
**Fix:** Either update the anchors to current line numbers, or (more robust against future drift)
drop the bare `:NNN` references and keep only the structural description, e.g. change "the :523
leniency, PRESERVED" to "the verdict-null leniency on the next line, PRESERVED". Same treatment
for the `:419`/`:429` and `:507` anchors.

### IN-02: Schema `claims[].id` row carries a dual AGG-1 / WR-04 label that future readers may find ambiguous

**File:** `plugins/lz-advisor/references/lz-deep-research-schema.md:147`
**Issue:** The relabel correctly moves the primary identifier to `AGG-1` and annotates "test
co-labeled WR-04 for the SC-4 acceptance anchor". This is internally accurate (the test is named

**Fix:** Optional. If the SC-4 acceptance anchor is retired in a later phase, collapse the row to
the single `AGG-1` label to remove the dual-ID ambiguity. No action needed now.
