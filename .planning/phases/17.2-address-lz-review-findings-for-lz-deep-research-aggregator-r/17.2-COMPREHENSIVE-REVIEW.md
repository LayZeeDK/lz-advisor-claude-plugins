## Important Findings

### I-1: `recheckClusters` silently narrows `sources` Set -- undocumented second under-count on `corroboration_lower_bound`

**File:** `lz-deep-research-aggregate.mjs:433-442`
**Schema:** `lz-deep-research-schema.md` (corroboration_lower_bound row)

`recheckClusters` rebuilds the cluster's `sources` Set from surviving members only:

```javascript
kept.push({
  ...cl,
  members: survivingMembers,
  quote_fidelity: hasVerified ? 'verified' : 'downgraded',
  sources: new Set(survivingMembers.map((m) => m.source)),  // rebuilt from survivors only
});
```

A 3-source cluster where 2 sources had fabricated quotes emits `corroboration_lower_bound: 1`
with no receipt. The post-recheck value is the correct semantic (only count sources with
verifiable quotes), but the schema's corroboration_lower_bound row cites `cluster.sources.size`
without clarifying this is the POST-recheck value. The summary gives no signal of the narrowing.

**Missing test:** No fixture has a multi-source cluster that partially drops members, reducing
`sources.size` before ranking. SC5-2 (single cluster, no rank competition) and SC5-4 (intact
2-source merge) cannot catch a regression here.

**Action:** Document post-recheck narrowing in schema corroboration_lower_bound row. Add a
fixture with a 3-source cluster where 1 source's sole member is quote-dropped, asserting the
survivor has `corroboration_lower_bound: 2` (not 3).

### I-2: No zero-claim test (empty or absent `claims/` directory)

**File:** `lz-deep-research-aggregate.test.mjs`

`listJson(claimsDir)` returns `[]` when the directory is absent or empty. `aggregate()` should
emit:
```
raw: 0 -> clusters: 0 (merged: 0)
quote-recheck: verified 0 | downgraded 0 | dropped 0
capped: none
survivors: 0 (High 0, Medium 0, Low 0, Contested 0, Unsupported 0)
```
with `{ survivors: [], dropped: [] }`. The existing `unsupported-no-votes` fixture exercises a
different path (one claim, no votes -> Unsupported). The zero-claim path is untested.

**Action:** Add a tmpdir-based test (no claims/ dir or empty claims/) asserting the `raw: 0`
summary line and empty survivors/dropped arrays.

### I-3: SC5-5 asserts SYNTH_CAP count (20) but not which 20 survive -- rank-order regression undetectable

**File:** `lz-deep-research-aggregate.test.mjs:524-542`

Current assertions:
```javascript
assert.match(r.summary, /claims \d+->24/);
assert.match(r.summary, /synth \d+->20/);
assert.equal(r.survivors.length, 20);
assert.equal(CEILINGS.SYNTH_CAP, 20);
```

None asserts which clusters are in `r.survivors[0..19]`. The `ceilings-enforced` fixture uses
NATO-phonetic claim texts (alpha, bravo, charlie...), all corroboration 1, so ranking is pure
lexical on `normalize(text)`. `cluster0` ("alpha...") and `cluster1` ("bravo...") sort first
deterministically. A swapped or reversed `rankClusters` order leaves all 4 assertions green.

**Action:** Add `assert.equal(r.survivors[0].id, 'cluster0')` and
`assert.equal(r.survivors[1].id, 'cluster1')` to SC5-5.

### I-4: Corroboration-DESC primary sort never exercised under the cap path

**File:** `lz-deep-research-aggregate.test.mjs:524-542`
**Code:** `lz-deep-research-aggregate.mjs:453-459`

The `ceilings-enforced` fixture assigns every cluster exactly 1 source (s01 through s31), making
all corroboration_lower_bound values equal. The primary sort key (`cb - ca`) at `:457` is always
0, so the tiebreak (lexical) is the only active sort dimension. A regression deleting the
corroboration-DESC branch passes SC5-5.

**Action:** Add one multi-source cluster to the `ceilings-enforced` fixture (or a new fixture)

### I-5: Downgrade-then-cap interaction unpinned -- no fixture crosses partial quote-drop with ranking+cap

**File:** `lz-deep-research-aggregate.test.mjs`

The pipeline order is: `recheckClusters` (narrows sources) -> `rankClusters` (uses post-recheck
sources.size) -> `enforceCeilings` (top 24) -> SYNTH_CAP (top 20). A cluster that starts at
corroboration 3 but drops to 1 after recheck could fall below the cap cutoff, changing which
claims reach synthesis. No fixture exercises this interaction:
- SC5-2: single-cluster fixture; no cap competition
- SC5-4: 2-source intact merge; no drop

**Action:** Add a fixture where a 3-source cluster has 2 sources' members quote-dropped, reducing
it to corroboration 1, and it competes near the cap cutoff against singletons it would have beaten
at corroboration 3.

### I-6: `tally()` runs on all 24 capped clusters before SYNTH_CAP drops to 20 -- `votes_ignored` provenance includes discarded clusters

**File:** `lz-deep-research-aggregate.mjs:619-636`

`tally()` is called inside `capped.map()` (line 621-628) which maps over all 24 post-claims-cap
clusters. `SYNTH_CAP` then slices to 20. Any extra vote seats on clusters 21-24 (those discarded
by SYNTH_CAP) accumulate into `caps.votes_ignored` even though those clusters never appear in
output. The schema documents this as a known scope caveat (AGG-4), but no test pins the behavior:

```
# schema: votes_ignored scope caveat -- counts from clusters 21-24 may appear
# even though those clusters were SYNTH_CAP-discarded
```

**Action:** Add an assertion in the ceilings-enforced test (or a new test) that `caps.votes_ignored`
is present even for clusters that don't survive SYNTH_CAP, documenting the provenance behavior.
Alternatively, clarify in a comment at line 621 that the map intentionally runs tally before the
synth cap.

## Suggestion Findings

### S-1: Schema marks `worker` as "yes" required but aggregator never reads or validates it

**File:** `lz-deep-research-schema.md` (~line 145)

The claim file table says `worker: string | yes | The producing worker id.` but `mergeClusters`
reads only `w.source` and `w.claims[]`. The `worker` field is never accessed. Unlike the fail-closed
fields (`source`, `id`, `text`, `quote`), a missing `worker` processes silently.

**Action:** Change the Required column for `worker` to "informational (not enforced by aggregator)"
or add a note: "Not read by the aggregator; for human readability / Phase 19 traceability only."

---

### S-2: Extra-seat counting loop in `tally()` has no upper bound

**File:** `lz-deep-research-aggregate.mjs:558-572`

The loop iterates from `CEILINGS.VOTES_PER_CLAIM` until the first gap, with no maximum. A
malicious or corrupted run-dir with thousands of sequential vote files would cause O(N)
`fs.existsSync` calls per cluster. The run-dir is a trust boundary.

**Action:** Add `s < CEILINGS.VOTES_PER_CLAIM + MAX_EXTRA_SCAN` (e.g., `+ 100`) as a guard, or
document the current behavior explicitly in a comment at line 558 acknowledging the unbounded scan.

---

### S-3: Cap boundary not pinned -- no assertion that last kept survivor precedes first dropped

**File:** `lz-deep-research-aggregate.test.mjs:524-542`

SC5-5 asserts count (20) and which clusters occupy positions 0 and 1 (per I-3 action), but
doesn't pin the cap boundary itself: that `survivors[19]` is the lowest-ranked survivor and that
the clusters 20-23 (post-claims-cap, pre-synth) are correctly excluded.

**Action (optional):** Assert `r.survivors[19].id` or that `survivors[survivors.length - 1]` has
a known id to pin the lower boundary.

### S-4: `quote_fidelity` does not influence rank order -- undocumented design decision

**File:** `lz-deep-research-aggregate.mjs:452-474` (rankClusters)

`rankClusters` sorts by `sources.size` DESC then lexical. A `verified` cluster and a `downgraded`
cluster with equal corroboration rank identically; fidelity never determines which survives the
cap. If intentional (fidelity is an output annotation, not a ranking input), add a one-line
comment at the sort to document the exclusion.

**Action:** Add comment: `// quote_fidelity is intentionally excluded from ranking; it is an output annotation, not a priority signal.`

## Questions

### Q-1: Should SYNTH_CAP and MAX_VERIFY_CLAIMS caps precede `tally()` to avoid running tally on discarded clusters?

**File:** `lz-deep-research-aggregate.mjs:619-636`

Current order: `enforceCeilings` (cap to 24) -> `tally()` for all 24 -> SYNTH_CAP (drop to 20).
`tally()` reads vote files from clusters 21-24 that are then discarded. An alternative order
(enforceCeilings -> SYNTH_CAP -> tally for final 20) would avoid that work and make `votes_ignored`
provenance cleaner. Tradeoff: the current order matches "count all caps observably" framing (D-11),
and reading vote files for 4 extra clusters is cheap. This is a design question, not a bug.

## Cross-Cutting Patterns

**Schema-vs-code drift on the corroboration mechanism (I-1, S-1):** The schema is the frozen
contract consumed by Phases 18 and 20. Two gaps: S-1 over-claims enforcement (`worker` "yes" but
ignored); I-1 under-claims a behavior (post-recheck source narrowing). Both are documentation
failures on the D-08/D-09 corroboration mechanism, not logic bugs. I-1 compounds because the
narrowing is invisible in the summary receipt -- no corroboration under-count can be detected from
output alone.

**Cap-membership unverified (I-3, I-4, I-5, S-3, S-5):** The suite tests cap COUNTS thoroughly
but never cap MEMBERSHIP. The `rankClusters` -> `enforceCeilings` -> SYNTH_CAP ordering pipeline
(the thing that determines which evidence reaches synthesis) has no end-to-end rank-correctness
test. A single fixture revision -- one multi-source cluster + id/boundary assertions -- closes
I-3, I-4, I-5, and S-3 together. S-5 needs a separate 22-cluster fixture.

**Fail-closed posture is sound:** The WR-01/02/03/AGG-1/R1-1/R2-1 validation posture is correct,
consistently applied, and correctly scoped to the run-dir trust boundary per CLAUDE.md guidelines.
`ContractError.file` discipline is uniform across all paths (AGG-5/6/7).
